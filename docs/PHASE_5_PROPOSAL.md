# 阶段 5：Recent Window 的持久化与恢复边界（已确认）

日期：2026-10-22。用户批准按讨论后的方案开发；积压多批改为同一次请求合并提醒、逐批提交。本文记录确认边界，不表示阶段 5 已通过验收。

## 第一部分：目的、范围与取舍

阶段 5 将已经完成的 Task、State、原文回读串成真正有界的模型上下文：按完整事件选取近期现场，给普通文字统一分配预算，必要时先提醒模型保存认知，再移出一批旧事件。用户仍使用原生 Pi，不增加模型调用或第二份聊天存储。

目前还缺一个规范明确留待本阶段确认的决定：**窗口的起点和待移出批次如何持久保存**。仅放在内存中，会在重启后重复提醒、重复移动，或者错误地重新载入已经退出窗口的内容。推荐以下边界：

1. **只在 Pi Session 中保存少量窗口定位信息。** 使用一种新的 `memweave.window.v1` custom 记录，记录当前边界、有效 N/B、待移出批次，以及准备／提交所对应的原生消息。消息正文继续只读 Pi Session；不新增 Window 文件。优点是天然跟随分支和 fork，恢复时有依据；代价是 Session 中会增加少量不发给模型的元数据。
2. **正常滑动处理一批；恢复时积压多批则在同一次请求中合并提醒，成功完成 assistant 和全部工具后按序提交。** 中断、模型错误、工具结果尚未齐备或边界落盘失败时，保留尚未提交的批次。State 工具失败仍按既定规则独立处理，不假称认知已保存。待移出内容临时可见，因此事件数可能超过 N，仍受半额 token 预算限制；不为每批额外发起模型请求。普通重启不凭空增加批次，只有尚未移出的实际事件超出容量才会产生多批。State 窗口管理是另一套独立机制，不混用批次。
3. **窗口设置继续只影响当前 Session／分支。** `recent_window_set` 沿用已批准的 scope 覆盖值。下一请求从原始历史重选最近 N 个完整事件，取消旧设置下尚未提交的窗口批次，再按新设置继续。已经提交的 State 不回退；Task 切换也不重置窗口。优点是扩大窗口能找回原文；代价是用户主动重设窗口后，先前移出的历史可以重新进入视野，这是现有扩大／缩小语义的实际结果。
4. **完整回读豁免只适用于紧接着的请求。** 根据原生 `memory_read` 工具结果的来源和机器标记识别，覆盖该 assistant 同轮的成功回读结果；网络重试复用这份请求。之后恢复普通 Q 截断，图片恢复为原件 R 引用。不是把任何自称“原文”的工具输出永久固定在上下文中。

预算实现继续采用已经定稿的 `C=floor(C_model/2)` 和唯一 Q 公式，不更改 200/40、State、最新用户不截断、工具配对或失败取消语义。没有匹配 tokenizer 时，采用保守估算并明确报告估算口径；它可能比供应商实际计数更早拒绝大请求。图片费用不能仅按 base64 字符数或 Pi 的固定图片估计值冒充精确 token 数，需要在适配层单独核验并保留余量；无法建立保守预算的模型／图片组合明确取消。

另一种可行方案是将起点与待处理批次放在独立 JSON 文件中，但会增加分支定位、并发协调和 Session 搬迁的一致性负担，也偏离既有“不新增 Window 日志”的方向。只保存已提交边界、不保存待处理批次，则难以保证失败重启后批次 ID 和候选集合保持稳定。因此推荐 Session custom 方案。

本提案不改变长期认知靠 State、短期现场靠 Window、完整经历靠 Session 的核心设计；不更改现有 State 事件格式、U/A/T/R 编号或发布方式。用户已确认新窗口元数据及积压批次的恢复方式。

## 第二部分：技术细节

### 依据与必须确认的缺口

- `ARCHITECTURE.md` §5 明确写明：“Recent Window 批次元数据的唯一持久化位置仍需在阶段 5 前确认；本次批准不扩展到该决定。”
- `IMPLEMENTATION_PLAN.md` 阶段 5 的进入条件是：“批次元数据/覆盖值的持久化位置已经确认”。覆盖值已在阶段 2 批准，Window 批次尚未批准。
- Recent Window §4.2 要求稳定 batch_id、提醒后提交、失败不重复推进；§4.3 要求可从 custom 或会话元数据恢复，但未定义记录结构。
- §4.2 的积压恢复时序经讨论确认为：同次展示、合并提醒、在该轮完整结束后按顺序提交各批，部分失败不重复推进已提交批次。

### 窗口记录

建议统一使用 `memweave.window.v1`，数据为完整的轻量窗口快照：

```ts
type WindowMetadata = {
  stage: "prepare" | "commit" | "reset";
  recent_turns: number;
  evict_turns: number;
  boundary_entry_id: string | null;
  pending: {
    batch_id: string;
    candidate_event_ids: string[];
  }[];
  request_anchor_entry_id: string | null;
  completed_by: string | null;
};
```

- `boundary_entry_id` 定位最后一个已移出事件的原生起始 entry；用户事件用 user entry，assistant 事件用 assistant entry。关联工具结果随整个事件一起移出。null 表示尚未移出。
- 候选数组只保存本批 B 个完整事件的原生起始 entry ID，不保存正文或另造消息编号。batch_id 由来源 Session、已有边界及候选身份稳定生成；同一待处理批次重试不换 ID。
- `request_anchor_entry_id` 定位准备本次请求前的最后一条原生消息，避免把其他请求的完成误认为本批提醒已被处理；不使用时间戳猜对应关系。
- `completed_by` 只在 commit 中记录完成本次提醒处理的原生 assistant entry ID。每个 commit 的 boundary 前移至该批最后一个事件，从 pending 中移除该批；已提交 batch 不二次移动。
- prepare 在需要提醒的请求准备阶段可靠追加；重新提醒仍引用同一批次。commit 在对应 `turn_end` 校验完整消息／工具结果后可靠追加；该追加成功是唯一窗口提交点。
- reset 用于有效 N/B 改变后的重选。设置改变在下一请求生效，按最近 N 个完整事件确定边界，不继承旧参数下的 pending。首次接入没有边界时从原始分支建立窗口；若超限，按 B 分批准备并合并提醒。历史正文和已提交 State 不改写。

读取当前分支祖先链上的最新合法记录，校验边界与候选确实属于该分支，且事件连续、顺序正确、工具结果配对完整。fork 继承分叉点之前的窗口状态，此后各自推进。tree 回退跟随所选祖先的窗口状态；不跨分支套用较新边界。旧 Session 没有窗口记录时按原始历史恢复，旧压缩摘要不作为真实事件；无法解释的表示明确诊断。

已有 `memweave.scope.v1` 仍保存六字段覆盖值；不另设全局当前窗口。工具写入 scope 后，下一请求将有效 N/B 与窗口快照对比并执行 reset。scope 已落盘但下一请求尚未发生时，重启仍可推导同一次重选，不要求设置和边界跨两个文件原子提交。同一原生调用重试要识别已完成的设置，不能覆盖之后的新设置；同轮存在冲突的多次窗口设置时明确拒绝，允许与普通 State 维护并行。

### 请求组装与预算

在现有一个 `context_with_system` 内，沿用同一 Task／配置／State／模型快照，依次执行 Rule 渲染、`window_select`、`window_allocate`、`window_render`、`state_insert`。

事件索引读取原始分支并与本次 `event.messages` 按原生来源匹配，不能只取磁盘快照而遗漏新消息。真实用户每条一事件；成功确定的 assistant 与其全部工具结果一事件。不完整的工具调用不拆成多个事件或单独移出。跨 Task 引用显示来源 Task；未绑定 Task 的消息不伪造 U/A/T 编号。需要把附件替换为 R、却尚无可用 Task 来源时，应明确诊断所缺的绑定，不静默丢弃附件或声称附件可回读。

R 使用渲染后的有效系统和工具声明；S 包括完整 State 和 State 提醒；O 以核验过的本次输出上限保守预留；H 包括包装、窗口提醒、安全余量及未在其他项计入的工具参数／推理／签名。U、X 与 H 不重复计数，M 仍包括已在 U/X 中预留的消息。普通多文字块共用一个 Q，仅裁普通正文；工具参数、原生关联 ID、推理／签名和图片块不按文字截断。

Pi 1.3.0 的普通主会话未显式设置输出上限时使用 model.maxTokens，原生层还会按剩余上下文收紧。保守预留不依赖这次收紧来突破半额 C。覆盖输出上限的模型 samplingParams 或其他扩展必须额外核验，不能只信目录值；不能识别时报告未支持组合。

X 从紧邻请求前已完成的原生工具回合取得，核对工具名、调用参数、实际返回范围及已登记的 `memweave_read` 结果。正文中的伪造标记无效。多个成功回读结果分别计入；失败项不因同批成功而冒充完整。网络重试不重新组装、不消费第二次；之后的新请求恢复普通策略。恢复、fork、reload 必须使用来源记录推导，不能只依赖内存的“已经读过”集合。

### 修改范围与验收

批准后先增量更新 Recent Window §3–5、Rule §3 的覆盖说明，以及架构／计划中的待确认项，再实现代码。固定 Rule 仅在确有协议文字变化时同步技术稿、独立模板及生成资源，不改核心记忆思想。

主要代码范围：`src/window/` 的事件选取／预算／渲染／批次逻辑，`src/pi/` 的来源与输出预算适配、窗口元数据，现有请求组装和扩展注册；必要时为 memory 内部附件定位增加复用入口，沿用既有 R 格式。新增的唯一公开工具仍是已定稿的 `recent_window_set`，不增加外部参数。

先写单测，再接 Pi 集成测试：200→201 与移出 40 的 161 事件例、工具配对、提醒阶段临时超限、扩大／缩小从原文恢复、重启／fork／tree、取消／失败／落盘故障、独立 State 提交、两类提醒并存、幂等、Unicode／多文字块截断、受保护字段、半额预算取消以及一次性 X 豁免。观察模型边界证明超限未发送，并检查原始消息未改写、State／提醒未持久化。

通过后使用仓库外 DeepSeek 配置验证真实 Window／State／回读闭环，并单列图片的真实预算与发送结果。临时验证代码、Session、图片和产物放在系统临时目录，成功失败均清理；正式回归测试保存在仓库。最后更新阶段验收记录，形成可读 commit 并推送。
