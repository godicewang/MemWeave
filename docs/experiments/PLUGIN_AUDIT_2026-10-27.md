本次能够完整配对的 SWE-bench Pro V2 四题，原生 Pi **4/4**，插件 Pi **3/4**。已观察到插件在 NodeBB 上以更少模型返回、更低模型费用达到相同官方成绩；尚未观察到插件通过而原生未通过的正确性 good case。Element Web 是明确的插件侧业务 bad case，且事后发现同一补丁还有单点降采样不终止的问题。

## 3. Good case：NodeBB 的同分低费用交付

**场景。** 给帖子 API 增加尊重读取权限与删除限制的原文、摘要接口，以及对应控制器。两份补丁均通过官方全部必需项。

**已观察到的优势。** 插件模型返回少 66.1%，Agent 时间少 65.9%，模型费用低 **45.1%**。它读取现有 socket/API 权限处理，完成三个业务文件的修改，启动 Redis 后实际运行 `test/posts.js`，得到 118 passing；随后成功保存三条 Fact，记录实现位置、权限边界和实测范围。没有用“文件已创建”代替“测试已执行”。

**为什么这次更省。** 原生轨迹花了多轮调试临时行为测试的加载和数据库 mock，还核对 `test/api.js` 的既有失败、添加三个 OpenAPI 文档文件。插件在多个模型返回中批量请求工具，探索和验证范围较窄，最终补丁只有三个业务文件。这里能够确认的是工作路径与范围不同；多工具同轮不自动证明并行执行，更不是 MemWeave 新增了一套调度能力。

**优势边界。** 原生最终实际通过六项临时定向行为测试；插件没有这组新增测试。两边本次官方成绩相同，因此可称为本样本的解题/API 费用 good case；不能称插件验证更全面，也不能称冷启动后的全流程更快。插件 Task/State 有效落库，但本题没有窗口移出或回读，无法证明省下的轮数由长期记忆造成。

证据：审计 JSON 的 NodeBB 两行与原件引用；插件 Session 第 59–67 行为实测、diff 与 State 提交，原生第 46–76、86–114 行为额外测试与文档过程。行号指 JSONL 物理行，不是 U/A/T 引用编号。

## 4. 有条件的 good case：Flipt 的较短等待

两边均完成 GitHub/OIDC 必填字段及错误格式校验，并通过官方判分。插件 Agent 时间低 **48.9%**，包含准备与重评分的单题墙钟低 **26.9%**，这是本次实测的时间优势。

代价是插件模型返回从 22 增至 28，模型费用高 **129.2%**。原生执行 `go build ./...` 及 `internal/server/auth/...`、`cmd/...` 回归；插件主要围绕 `internal/config` 编译和测试，并有一次 300 秒构建/测试超时后继续处理。两边都为新验证增加了 fixture 和测试，不能把插件描述为完全没写测试。

原生首次 config 测试所在工具区间约 524 秒，后续全量 build 所在返回批次约 621 秒。工具消息可能同批返回：同一 assistant 中另一个很短的 grep 也出现约 621 秒的 call/result 间隔。**这些间隔不能累加为各命令独占耗时，不能据此声称 grep 花了十分钟。** 审计 JSON 明确使用 `call_to_result_seconds`，最终阶段时间来自 Harbor 原始时间戳。

插件还将认证 method 校验移到了 session domain 校验之前；原生未移动这一全局顺序。该差异可能影响同时缺少多个字段时首先返回哪个错误，本次官方接受两份结果，尚无证据判它是额外功能缺陷。更短等待包含验证范围、方案和编译状态差异，不能归因于记忆读写速度。

## 5. Bad case：Element Web 的需求边界遗漏

### 5.1 原计划内已经发生的失败

任务明确要求平滑中间序列排除端点，且后续重采样不额外合成端点。插件却用 `[working[0]]` 初始化中间序列，并追加末值。官方 `arraySmoothingResample / should downsample` 期望 `[1,1,2,1]`，实际为 `[2,1,1,0]`；必需项 6/7，完整 Jest 32/33，按官方“全部必需项通过”规则得 0。原生为 1，控制为 oracle=1/nop=0，无评分异常。

直接原因是实际算法违反端点约束。可观察的验证缺口是：插件只改 `src/utils/arrays.ts`，运行原有 29 项测试，未增加覆盖新函数的断言；原生新增测试并最终运行 36 项。原有 29 项通过是事实，但没有覆盖本次新增行为。

插件把“旧套件 29 项通过”及实现 Decision 成功写入 State，最后说实现完成并已保存。**保存操作成功与业务验收充分是两件事。** 这里不是未执行测试就伪造通过，也不是 State 丢写；问题在于把局部验证当成足够的交付依据。Element Web 的 Task/Window 只有约 10 个完整事件，边界为 null，不能把此错误归因于成批移出了原始需求。没有请求级完整视图，也不作更宽泛的所有上下文变换因果断言。

### 5.2 事后核对：同一缺陷还导致不终止

原样插件函数对 `[1,2,3]`、目标 `points=1`，每轮仍产生 `[1,2,3]`：首值 1、邻居均值 2、末值 3。长度恒为 3，而退出条件要求不大于 2，所以循环永不收敛。这是代码的固定点，不仅是一次机器较慢造成的超时。

实际程序核对直接从两份冻结补丁提取函数，复用原 Session 读到的原始 `arrayFastResample`；在同版本 Node 24.22.0 下只剥离 TypeScript 类型和模块 export，函数体不改，使用隔离 VM 的 500ms 上限防止审计本身挂死。三个输入各执行三次，结果一致：

| 事后输入 | 原生产物 | 插件产物 |
|---|---|---|
| `[1,2,3]` → 3 点，提取/运行控制 | `[1,2,3]` | `[1,2,3]` |
| `[1,2,3]` → 1 点 | `[2]` | 三次均 `ERR_SCRIPT_EXECUTION_TIMEOUT`；静态固定点证实不收敛 |
| `[1,2,3,4,5,6]` → 2 点 | `[2,4]` | `[1,4]`，仍受保留端点影响 |

这些是**事后诊断**，不是重新跑 Agent 或新增官方测试成绩。源补丁和函数哈希、运行时、输入、重复结果均在 [诊断 JSON](results/element-posthoc-20261027.json)；原分数仍为 1/0。不能把两个症状算作两个独立的公开失败样本。

### 5.3 原因分层

| 结论层级 | 本次支持什么 |
|---|---|
| 已证实的直接原因 | 额外保留端点，改变数值序列并破坏单点降采样的长度收敛 |
| 已证实的过程缺口 | 没有新增新函数测试；旧套件通过后结束，并把局部结果保存为认知 |
| 尚未证明的解释 | Rule 变长导致忽略约束、State 强化错误方案、模型随机探索偏差，均无消融证据 |
| 不能据此指控 | 存储丢写、Task 恢复错误、Window 成批丢失需求、官方评分格式不兼容 |

已将该案例及后续验收边界补入 [MW-011](../DIFFICULT_CASES.md)。本轮不修补候选程序，也不通过事后补测刷新成绩。

### 5.4 早期 NodeBB：官方通过，但额外放宽删除帖例外

旧冒烟插件 `getRaw` 的删除帖分支将以下条件做了逻辑或：`posts:view_deleted`、管理员、版主。题目只允许管理员或版主作为例外。正式四题插件以及两次完整运行中的原生补丁均无该额外放行条件。

对四份原样 `getRaw` 函数做离线依赖桩核对：固定帖子已删除、调用者有主题读取权限、不是管理员/版主，但 `posts:view_deleted=true`。旧插件返回夹具原文，其余三份返回 `null`。普通读取、管理员、版主和无主题读取四类控制也逐一检查；五个条件、四个函数各三次，共60次，结果稳定，仅旧插件的这一组合不符合文字要求。完整程序、源补丁/函数哈希和输出见 [权限诊断 JSON](results/nodebb-posthoc-20261027.json)。

这个反例证明了函数在给定公开接口返回条件下的分支行为；没有在完整 NodeBB 数据库中配置并验证该权限组合的可达性，不宣称已经复现真实部署漏洞。原官方1分保留，另列需求符合性问题，不篡改官方评分或把它计入正式四题的0分数量。

已证实的直接问题是将通用的“可看删除帖”权限与管理员/版主身份视为等价例外。旧 State 的 Decision 反而写了“删除帖仅管理员/版主可读”，说明保存了正确文字约束也不保证生成代码遵循它。模型未执行业务测试，只做ESLint；这是可见的验证覆盖不足，不是 State 未保存。Rule负担、记忆强化等内部解释依然没有因果证据。本业务函数来自受测仓库，不是 MemWeave 自身的权限实现。已一并补入 MW-011。

## 6. 插件自身运行情况

| Pro 任务 | task_create / task_find | state_append 尝试 / 成功 | 归档中的 F / D | Window 成批移动 |
|---|---:|---:|---:|---:|
| NodeBB | 1 / 0 | 1 / 1 | 3 / 0 | 0 |
| Ansible | 1 / 0 | 2 / 1 | 1 / 1 | 0 |
| Element Web | 1 / 0 | 1 / 1 | 2 / 1 | 0 |
| Flipt | 1 / 0 | 0 / 0 | 0 / 0 | 0 |

**确定有效的保护。** Ansible 第一批 State 的 Decision 长 106 字符，程序返回 `STATE_CONTENT_TOO_LONG`、actual=106/max=100；下一次缩短并保留必填字段后提交成功，归档最终只有 Goal＋1D＋1F，没有非法内容或重复 Fact。是一次已恢复的模型工具误用，已补入 MW-002；不能为了降低报错数就放宽 100 字符契约。

早期完整 NodeBB 冒烟也有一次110字符被拒后成功缩短，最终为 Goal＋1F＋1D；在相同工具边界上观察到另一独立的已恢复误用。它未混入上表正式四题的调用数量。
