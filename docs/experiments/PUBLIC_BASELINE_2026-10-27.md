### Element Web 失败分析

插件补丁的平滑阶段先放入首值，随后追加末值，与任务明确要求的中间序列排除端点冲突。官方 `arraySmoothingResample / should downsample` 断言期望 `[1,1,2,1]`，实际为 `[2,1,1,0]`。官方必需项为 6/7 通过，完整 Jest 执行为 32/33 通过，评分按全部必需项通过的规则为 0；无评分异常。相同环境中 oracle=1、nop=0、原生补丁=1，因此没有把格式或容器兼容失败当成模型错误。

插件真实运行过原有 `arrays-test.ts`，29/29 通过，并在 State 中记录了这个有输出依据的事实；但没有新增覆盖新函数的测试。原生补丁新增了平滑/缩放测试。这次差异说明需求理解和验证覆盖不足：旧测试通过不能代表新行为已验收。它不是“未运行测试却伪造通过”，也不能仅凭这个样本断言 MemWeave 的某个内部机制导致了错误。

具体原件见运行根中的 `harbor/pi-memweave-r1-regrade/instance_element-hq__element-web__TJThMBy/verifier/run-script-stdout.txt`、`test-stdout.txt`，以及 `harbor/pi-memweave-r1/instance_element-hq__element-web__7K7fLN2/agent/model.patch`。这份补丁和失败保留，不修改后沿用本次成绩。

事件按“一条真实用户消息”或“一次 assistant 返回及其全部工具结果”计数。两边均无 compaction；插件四题的窗口记录均为 N=200/B=40、`boundary_entry_id=null`、`pending=[]`，没有成批移出，且没有 `memory_read`、`task_resume` 或 State 压力场景。不能把本次累计输入差值归因于滑窗移除；原件也不保存完整请求级临时视图，不据此宣称量化了所有单消息截断。

插件首轮输入分别为 9,530 / 10,100 / 9,799 / 9,331 token，原生为 2,246 / 2,815 / 2,515 / 2,047，差约 7,284 token。它反映本组合完整协议、额外工具与请求状态等的整体开销，不能拆成纯 Rule 文本开销。对这类短任务，该开销需要靠后续行为收益抵消。

Ansible 首次 `state_append` 内容为 106 个 Unicode 字符，工具按 100 字符上限拒绝，后续重试成功。Flipt 没有追加 State，只有 Task 创建。这些是实际记忆行为，不因缺少某种记忆操作而另扣官方题分。原生也有工具错误：NodeBB 的 bash 1 次、Element Web 的 bash 1 次、Flipt 的 edit 1 次，均在同一次尝试内继续处理。过程错误与最终判分分别记录。

需要用户确认的依据是根 AGENTS.md 第 2 节及 [实验设计第 3 节](IMPLEMENTATION_DESIGN.md)：任务转换与镜像冻结边界出现多个合理实现时须先对齐。提案尚未获答复，本轮没有实施该接入变化。后续继续时仍须核对剩余整体时限，不自动追加预算。

## 解释边界

这是按本机 CPU、内存和平台条件筛选的小规模公开子集，不代表全量榜单。每题只运行一次，不能据此宣称统计优势。两边完整产品上下文策略不同，结果也不是单一窗口算法的消融。

本次顺序为原生 Pi、原生补丁重评分、插件 Pi、插件补丁重评分。容器与记忆冷启动不等于供应商缓存冷启动；运行顺序、服务端负载、缓存状态和模型随机性都可能影响费用与耗时。仿真时间也不能直接外推为原生 Linux 上的性能。

记忆收益需要结合实际窗口压力、回读、Task / State 调用及业务错误判断。本次主要观察到探索轮数、测试范围和固定提示开销的差异，尚未测量跨会话恢复或长程遗忘。下一步可预先固定更多分层任务与重复次数，并在 local_baseline 中专门覆盖新需求测试、端点约束及跨窗口持续任务；本报告不把这些建议视为已实施或新增付费运行的授权。

此前单题链路冒烟 `20261026T165811Z-9853d73783` 的两边均通过，另见 [验收记录](VALIDATION.md)。它用于确认执行链路，不与本次新运行拼接为更多独立任务；此前失败尝试也保留，不作为 best-of-N 的候选。
