## 第一部分：效果、问题和建议

### 总体判断

常规业务、主动预算阻断、真实回读/视觉、State 滑动和 8 个独立 Pi 进程的小历史并发均可工作。真实编程任务的三次运行都通过 7 项独立校验，测试文件没有被改写；10 轮长任务最终 9 个字段全部正确。

不能据此称为“长期运行已无问题”。新增压力测试发现：超大批次积压可能持续阻止模型运行；取消后的连续用户指令在 DeepSeek 上存在顺序歧义；State 的活动条数有界，但本机重放和写入成本仍随完整历史增长。记忆工具的实际调用和写入质量，也不能由任务最终答案正确来代替验收。

共执行 **97 次真实 DeepSeek Flash 推理**，包括对照和边界探测；另有明确标记的 Faux/本地 HTTP 准备，不计入真实调用。83 次带逐请求预算/usage 记录的真实请求未发现实际输入＋输出预留＋基础安全＋池内安全超过上限；其余包括两个绕过插件的提供方对照，以及既有真实专项/实际产物用例。

### 必须优先处理 1：超大积压会堵住自己的恢复通道

**实测。** 在已有 Window 元数据之后，模拟插件停用期间追加 26000 条短用户记录，再恢复。同一会话连续两次得到 CONTEXT_BUDGET_EXCEEDED，模型调用数都是 0。原始记录没有变化；把用户配置 N 从 200 改为 199 后，后续请求可以发送。

**为什么。** [窗口选取](../src/window/select.ts)第 92–128 行保留整个可见历史，并把所有待移出批次同时纳入提醒请求；本轮结束后才允许提交边界。大量积压不仅占正文，还产生不能裁剪的逐消息协议成本和最小引用/tag 成本。一旦准备阶段超限，assistant 无法运行，提交也不会发生；重试仍面对同一积压。模型需要运行才能调用 recent_window_set，但目前连该次运行都进不去。

200 改 199 的效果来自“参数变化触发 reset、从原件重选、取消旧 pending”，不是少一条记录节省出了大量 token。当前错误文字只建议缩输入/回读或换大模型整理 State，不能准确指出这里是 Window 积压，尤其本例没有 State。

**推荐。** 短期提供无需模型推理的显式“从原历史重选 Window”恢复入口，并显示积压批数、消息数和真正超限分区。根治方案是按本轮预算容纳的数量，有界地展示若干待处理批次并提交已处理部分，后续继续；不必每 40 条单独调用一次模型，也不能自动删除原文或假称已检查旧内容。该方案改变当前“积压同次全部提醒/提交”契约，必须先对齐设计和恢复语义。

### 必须优先处理 2：取消后恢复，最新指令可能被旧指令抢走

**实测。** 缩小总预算、固定 N=200，先后提交只回复 FIRST_EXPECT、SECOND_EXPECT，两次均取消；人工重选 N=199 后提交 THIRD_EXPECT。真实提供方 payload 中包含 FIRST、SECOND、THIRD，且顺序正确，模型却回复 FIRST_EXPECT。独立复测仍如此，下一次正常请求 FOURTH_EXPECT 才正确。默认 26000 条积压案例也回答了较早的 BACKLOG_OK。

**原理与归因。** [事件索引](../src/window/select.ts)第 34–38 行跳过失败/中断 assistant，同时原始用户消息正确保留。因此恢复时可能出现多条连续、相互冲突的用户指令。这不是插件漏发最新消息：出站 payload 已直接确认。为排除程序丢消息，另做了两次 Pi ModelRuntime 直接调用：无插件、只有 FIRST/SECOND/THIRD 三条连续用户消息时，DeepSeek 同样回复 FIRST；加上明确的“冲突时只服从最新真实用户消息”系统说明后，该对照回复 THIRD。

这里的根因判断限于观察到的连续用户指令歧义，不能推出所有供应商或所有取消情况都会出错。

**推荐。** 在固定 Rule 中明确最新真实用户要求相对旧冲突要求的优先级；由程序用已有真实 U 引用/来源定位说明当前请求，不能让模型误把末尾 State 当作最新用户。补上“两次取消→修复配置→新指令”的真实模型回归。不能为了避免歧义删除原始用户消息，也不能仅重试旧输入。改 Rule 需先确认并同步两份模板；一次最小对照成功不代表该改动已在完整插件中验收。

### 需要解决的长期扩展问题：500 条活动窗口不能限制 State 的本机成本

**实测。** 下表均先把活动认知控制在约 500 条，保留完整历史；每种规模测 5 次，取中位数。是本机 StateStore/I/O 压力，没有调用供应商。

| 历史 Fact 数 | State 文件 bytes | 单次读取/重放 ms | 单次追加并可靠写入 ms |
|---:|---:|---:|---:|
| 500 | 134989 | 4.17 | 18.95 |
| 5000 | 1345227 | 38.09 | 87.27 |
| 50000 | 13490234 | 401.44 | 809.15 |

在最后一档同时发起 32 个写入，约 15.13 秒后 19 个成功、13 个明确 LOCK_TIMEOUT。最终日志准确包含 19 个并发标记，没有把失败的 13 个伪报成功。正常小历史下的 8 进程真实测试全部成功，两者不矛盾。

**为什么。** [StateStore.read](../src/state/store.ts)第 40–50 行每次读取整个 JSONL 并重放；append 先重放旧日志，再取完整旧字节、重放新结果，最后原子替换整个文件。窗口只限制呈现的活动认知，不限制这些工作。再叠加 [互斥锁](../src/storage/files.ts)固定 15 秒等待，长日志下并发队列容易超过等待时间。这是吞吐与恢复体验问题，当前没有数据损坏证据。

**推荐。** 优先做有界的 Task 重放缓存和 op_id 查找索引，只增量处理经过验证的新记录；跨进程、文件替换或前缀不一致时重新核验，保留现有幂等与原子提交。先用相同 5 万历史/32 写入复测，不以单纯延长锁超时掩盖重复工作。进一步分段日志或新增持久 checkpoint 会改变存储协议，成本更高，应另行讨论。若暂不优化，至少明确支持负载与可诊断的超时/重试流程，不能宣称逻辑窗口让所有本机成本固定。

### 可优化 1：任务完成不等于关键认知已经保存

三次真实编程都做对了，但普通提示的一次运行完全没有 Task；另一次只有 Goal。显式要求先创建 Task 的运行最终也只有 Goal，没有 Fact/Decision。相反，十轮出货任务确实调用记忆工具并保留了跨窗口约束。

原因是创建 Task、选择何时保存重要结果主要依赖模型执行 Rule；结束处理只同步来源和提交 Window，不会证明已保存本轮重要认知。Task 为空或 State 没有变化时，业务工具仍能正常工作。不能把这解释成所有短任务都必须记录流水账，也不能据此自动生成事实。

建议明确首次实质任务的绑定指引，增加“是否有应保存的重要结果”的轻量闭环验收，并提供可选诊断查看 Task 绑定和 State 版本；不改当前简洁的默认状态显示。重点测测试结论/关键约束是否留存，避免强制每条消息写一条记忆。若产品希望保证某种落盘覆盖率，需要先明确这项承诺，不能只依靠提示词宣称保证。

### 可优化 2：把工具的关键约束说得更清楚

十轮任务中两次 state_append 漏掉必填 items[].type，被原生校验拒绝；模型补齐后继续，最终答案正确。显式创建 Task 的编程运行还一次超出 Goal 的默认 100 字符上限，缩短后成功。

[工具描述](../src/extension/register.ts)明确写了 content/evidence，却没有同样强调 type；task_create 描述也没有指出 Goal 同样受当前 State 正文限额约束。schema 虽然严格，模型仍会生成不合法参数；这是额外工具轮、延迟和 token 成本，不是静默写入。

建议在稳定工具描述/最小示例中明确 type=fact/decision、Goal 使用当前快照字符限额；错误返回 actual/max 等可操作信息。保留严格校验，不自动把缺 type 的条目猜为 Fact，也不把可配置上限 100 永久写死到静态 schema。

额外工具禁用对照：主动关闭所有记忆工具、同时保留满 State 管理提醒时，模型曾输出裸 DSML 函数文本，没有真实执行。恢复 state_remain 后同样的历史场景完成。该对照不计默认配置故障，但提示应为“不支持的工具 loadout”提供明确诊断，不能擅自重新启用用户关闭的工具。

### 可优化 3：大正文准备时间与按负载配置

默认输出预留的稠密 Window 样例，请求准备约 1.84 秒；同机官方 tokenizer 的独立预算/渲染脚本约 920.2 ms（5 次中位数，401 条消息、1.525 MB），UTF-8 保守计数约 28.6 ms。后者计量不同，不能拿来替代匹配 tokenizer。旧策略在同一脚本中约 732.2 ms，但两种策略展示量不同，不能当作等输出算法性能对比。

准备耗时包含分词、前缀候选/复核、历史比较与复制，以及模型元数据请求，不能全归到某一个函数。可以先剖析热点，再在单请求内复用编码/计数结果；请求结束释放，不新增长期正文/token ID 缓存，不降低最终 token 复核。

默认稠密样例读池约 29.3 万 token 没使用，普通池仍不能借它，所以实际 API 输入约 29.57 万而非填到 80%。这是用户已确认的隔离策略，不是容量丢失。偏纯编码/少回读的任务可由用户明确选择更偏 Window 的比例配置；不能在实现中静默借出回读池或安全池。

## 第二部分：执行证据与边界

### 方法

- 新增场景通过 Pi 原生 AgentSession/ModelRuntime、正式 registerMemweave、原生 SessionManager 和真实 DeepSeek Flash 执行。临时工作区使用 Pi 默认系统提示，不加载开发仓库 AGENTS/规范作为业务提示。编程工具来自 Pi 公开定义，测试执行器只运行临时项目固定测试。
- 自主任务从真实模型开始，未用 Faux 代写答案。大历史、满 State、并发绑定和回读准备采用明确标记的合成历史/Faux；之后的模型调用、工具参数、行为选择和 usage 均为真实供应商结果。
- 常规场景为控制输出成本显式设置 4096 tokens，轻负荷/回显场景为 256，并发写入为 512；另单独执行了默认输出 62914 的稠密样例。表中已区分，不能把显式输出 256 的 32 万输入当成完全默认配置。
- 1/4/8 并发为实际独立 Node/Pi 进程；32 写入为本机同进程并发 StateStore 调用，分别衡量供应商/宿主组合与锁/存储排队，不等同于 32 个真实 API 客户端。
- 测量准备时间从 context_with_system 开始到 before_provider_request，包含元数据 GET；记录 API usage 时合计普通 input、cacheRead、cacheWrite。最大本地输入低估 1225 tokens，基础安全余量覆盖；未据此宣称整个供应商模板可逐 token 精确计数。
- 不保存密钥、完整真实请求或 Session 到仓库。私有认证文件测试前后字节一致；临时 config/Rule/Session/State/项目位于系统临时目录，不改本机真实记忆。

### 内存与完整性

- 1000/10000/50000 条已有历史的单次真实请求中，实际只选约 201 条；准备约 303/139/377 ms，单次冷热不同，不做严格倍率结论。对应进程 RSS 约 312/383/516 MiB，含 Pi 全历史及运行时，不能当成新增缓存体积或泄漏证据。
- 来源缓存在 10000 条记录上连续 20 次复制/核验后，保持 8192 项、估算 4742480 bytes；GC 后堆约 99.15–99.40 MiB，最后比首次少约 0.24 MiB。该样本未观察到持续增长，不保证整个 Pi 在任意运行时长都恒定。
- 活跃/到期回读和大正文的预算约束在被记录的真实请求中保持；超大最新用户与积压都在提供方调用前取消。
- 原始大消息、抽样旧历史和视觉原件检查未发现本插件改写；被拒绝的写入没有冒充成功。长历史的合法 state_remain 会追加滑动记录，是预期写入，不能要求该文件完全不变。

### 未验证或不能外推

没有数小时/数周 soak、统计性长期任务成功率、供应商持续 QPS/RPM 上限、任意第三方扩展、其他模型或本轮 Pi 1.3.0 重验。未逐项人工判定所有 F/D 的证据蕴含关系，引用存在性校验不能代替语义真实性验证。启动 UI 的自动回归包含在完整入口，本轮没有重做真实 TUI 人工专项。压力数据含合成内容；纯回显、随机 OCR 与小项目修复不代表所有业务质量。

优先顺序建议：先解决积压恢复通道和失败后的最新请求语义，再处理 State 长历史成本；随后提升记忆落盘可观察性、工具合规性和大正文准备效率。上述行为/文档调整均待用户对齐，本轮未代为实施。
