# 阶段 3：State 窗口与恢复边界（已确认）

日期：2026-10-21。用户已同意方案，并修正满窗行为：提醒的同时正常载入新认知，允许暂时超过 2000；不引入排队。以下为确认后的方案。

## 第一部分：目的、范围与取舍

目标是补齐 State 工具，并让“2000 个事件、每批管理 200 个、最多保留 20 个”在并发写入、重试和重启后仍有唯一解释。确认前的规范已明确上限和提交点，但没有确定窗口到底数什么、窗口已满时新认知放在哪里，以及如何恢复模型已经看到的待处理批次。这些选择会影响实际可见内容和数据恢复，不能只当作函数内部细节。

推荐统一以下边界：

1. **2000 个指当前可见的 Fact/Decision，当前 Goal 始终保留，单独呈现。** Goal 更新、归档动作和滑动记录仍递增 State 版本，但不占 Fact/Decision 的可见名额。达到 2000 时给出管理提醒。
2. **满窗时提醒模型管理，同时正常载入新增认知，允许暂时超过 2000。** 不排队、不截断新增 State、不自动移除旧候选。成功提交本批后再移除未保留候选；如果仍达到容量，下一请求提示新的批次。代价是待处理期间 State 可能超出名义容量，仍须服从最终请求 token 预算，不能静默截断 State。
3. **本批被保留的事件维持原来的时间顺序。** 下一次满窗时，它们仍可能再次进入最早候选，需要重新判断；不会自动变成永久钉住的事实。另一方案是把保留项移到窗口尾部，重复提醒较少，但会改变事件时间顺序和恢复规则，因此暂不推荐。
4. **将待处理批次的少量定位信息写入 Pi custom 元数据。** 不保存提醒正文或 State 副本，不新增记忆文件。这样重启后仍能辨认某个原生工具调用处理的是哪一批；并发进程已经改变候选时，拒绝旧批次并在下次请求重新提示，绝不悄悄拿旧选择处理新批。代价是待管理期间 Session 会多出少量扩展元数据。另一方案只放内存，实现更少，但不能可靠恢复旧调用，不能满足既定恢复要求。

`modify_fact` 推荐允许归档任何已记录、尚未被归档的 F/D（包括已退出可见窗口的条目），拒绝重复 ID、未知 ID 和已归档 ID；它必须同时新增一个 Fact。历史条目仍可作为 evidence。这个边界避免重复修正同一旧事实，也保留对历史认知的纠正能力。

不改变 Goal/Fact/Decision 三类认知、Task 共享 State、原始 Pi 历史、2000/100/200/20 默认值、五个 State 工具的既有参数或 State/Recent Window 独立提交。Recent Window 仍留在阶段 5。

## 第二部分：技术细节

### 依据与缺口

- `docs/specs/2.pi_long_task_agent_symbolic_state_v1_0_final_cn_updated.md` §7 写“事件达到 2000”及最早 200 个候选；§8 只呈现当前 Goal/Facts/Decisions；§14 将 state_version 定义为全部已提交操作数。规范没有给出这三个计数的对应关系。
- 同文 §9 明确允许 `state_remain` 与 `state_append` 在同一轮独立提交，没有给出满窗时 append 先执行的容量处理。
- 同文 §7/§9 要求失败保留批次、成功后才移除提醒，但只有 committed 的 slide_window 持久化示例，没有定义请求批次和原生 assistant/tool call 的关联。
- 同文 §6 要求 archive+append 原子提交，但没有明确已退出窗口或已归档 ID 的再次归档边界。

### 推荐的计数与重放

- `state_version` 保持全部成功操作记录数；F/D ID 按完整历史继续编号，不复用。
- reducer 重放全部事件，维护未归档、未被滑动移出的 F/D 有序集合；请求展示全部当前活动 F/D（包括满窗后新增项），允许临时超过 N；当前 Goal 独立保留。
- 可见数达到 N 时，候选为其最早 `min(state_evict_batch, 当前活动数)` 项；实际保留限额仍为 `min(floor(可见数/10), state_keep_limit, 候选数)`。
- 滑动沿用既有 `slide_window` 结构；evicted_range 使用原始 State 操作记录的 1-based 序号，表示本批候选的首尾位置。范围内已经归档或已移出的历史记录不重新激活；retained_ids 必须属于本批当前有效候选。保留项不重编号、不改原序。
- 同批 append 不改变已经给模型看的候选前缀；modify_fact 若改变候选，则旧批次显式过期。提交用 Task 写锁和稳定批次标识比较，不依赖工具并行的执行先后。

### 请求批次定位

新增 Pi custom 类型 `memweave.state.request.v1`，仅在需要管理时登记 `{task_id, batch_id, evicted_range, candidate_ids, keep_limit, state_max_events, state_evict_batch}`。不包含 State 正文、证据正文或提醒文案。

该记录位于本次原生 assistant 的祖先链中，工具通过来源 assistant entry 定位它。state_remain 参数仍只有 event_ids；程序负责获取 batch_id。batch_id 由 Task、上次已提交滑动和本批候选等确定，不使用每轮时间生成。成功只向 state.json 追加已有的 committed slide_window；同批重试读取已提交记录，不再滑动。Session 定位写入不可靠时主动取消，不发送一个无法恢复批次的请求。

### Goal 与索引

update_goal 继续使用既有 `{op_id, op, time, goal, evidence}`，不把摘要等字段塞进 State 事件。索引更新失败按部分提交报告；恢复时可由已登记原生 Session 的工具参数及 op_id 找回最新 Goal 对应的摘要、关键词和可选项目名，避免旧调用重试覆盖新 Goal 的发现信息。

### 同步与验收范围

先最小更新 State §6/§7/§9、Rule 技术稿相关说明及固定模板的必要措辞（两份模板同步），再实现窗口。测试覆盖默认 2000/200/20、空保留、非法范围/数量、临时超容量与新增认知可见、并发 append/remain、归档使候选过期、Session 重开、批次写入失败与同批重试；真实模型验证继续用仓库外 DeepSeek 配置。此前独立实现的 Goal 更新与 State 读取继续复用，不改变其既定行为。
