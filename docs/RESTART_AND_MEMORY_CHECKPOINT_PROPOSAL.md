# 近期历史新任务与阶段记忆闭环：待确认方案

状态：2026-10-25 用户要求评估和提供方案，尚未修改这两部分运行实现。本轮实际修复另见 REQUEST_PRIORITY_PERFORMANCE.md；回读池隔离不调整。

## 第一部分：目的、改动范围和取舍

### A. 从近期现场重新开始一个 Task

原压力测试增加的是 Pi SessionManager 中 26000 条原生格式的合成 user 记录，模拟没有 MemWeave 窗口管理时的历史增长；不是 State 日志，也不是真实调用模型 26000 轮。Recent Window 是从这些原记录选出的视图，不是一份物理聊天文件。该极限样例没有绑定 Task，也没有 State；即使存在旧 Task，停用期也不会自动生成新的 State 记录。

用户建议的新 Task 冷启动适合“此前记忆不再作为当前工作起点”的明确重新开始。建议保留旧 Task 及其全部 State，只让当前 Session/分支切换到新的 Task；新 Task 的 F/D 为空，由 Agent 根据近期原文和最新真实用户要求生成新 Goal。这里的“清空”指不再注入旧 State，不能删除旧 Task 的认知，避免影响其他仍绑定它的会话。

不建议仅凭停用时间或历史变多自动认定目标改变：继续同一目标的原生 Pi 工作、取消/崩溃重试和手工导入均可能表现为没有窗口提交。当前模式选择不保存完整启停区间，无法可靠判定是哪种。推荐显式“从近期新建 Task”的恢复入口；用户若要自动触发，应先确认识别条件和启停标记，不能以异常积压代替任务语义。

新入口应先在不调用模型的情况下完成近期范围重选和旧绑定退出，确保第一轮能发送，再让 Agent 创建有新 Goal 的 Task。不能先等模型调用 task_create，因为当前问题正是第一轮发送不了。

优点是放弃积压检查、迅速获得新的工作现场；代价是旧窗口之外尚未写入 State 的信息不再主动呈现，要按引用回读；自动推断的新 Goal 也可能不准，含糊时应询问。该流程涉及绑定/窗口冷启动和恢复，需单独确认后同步规范。

### B. 阶段结束与记忆验收

建议使用“模型判断阶段节点＋一份短闭环检查”，不新增工作流引擎、Plan 类型、独立总结 Agent 或每轮自动写入。阶段由当前用户要求中的可交付结果确定，例如完成一个模块并运行指定检查、查明根因并给出证据、交付比较结论。

程序的 turn_end 只说明一次 assistant 和工具结束，不等于一个阶段完成；stopReason=stop 也可能只是提问、解释或等待用户。用户没有要求“先征求验收”时不额外强制询问；Agent 根据已约定标准自行验证并如实报告，不能拿“模型说完成了”代替证据。

优点是覆盖关键认知，同时维持“模型决定什么重要”。代价是需要模型做一个简短收尾检查、必要时多一次批量 State 写入；不能承诺所有模型、所有任务绝不漏记。硬性保存覆盖率若要作为产品保证，需要另行定义，不通过自动造事实兜底。

## 第二部分：具体流程、指引和验收

### A. 新 Task 冷启动边界

1. 显式从当前分支原始消息索引选最近 N 个完整事件，取消旧 pending；不删除原始 Session、压缩记录或旧 Task State。
2. 若选中事件没有真实 user，找到分支中最近的真实 user，作为选中列表最早一项。为保持最多 N 个事件，应保留“该用户＋末尾 N-1 个完整事件”；N=1 则只保留用户。不得拆 assistant/工具结果，不能额外变成 N+1。分支完全没有 user 时，等待新输入，不猜 Goal。
3. 旧绑定退出只影响当前 Session/分支；不暂停、删除或回退其他 Session 正使用的旧 Task。旧消息仍保留原 Task 引用/归属，不给新 Task 偷换 U/A/T。
4. 在无旧 State 的受控冷启动请求里，让 Agent 基于该近期视图和最新要求调用既有 task_create，提供简短新 Goal 和完整元数据。新 Task 从初始 Goal（v1）开始，不要求先创建一个没有 Goal 的损坏 State。
5. Goal 有歧义时询问；未创建成功不假装已经绑定。重启、取消、部分提交必须恢复同一冷启动范围/创建操作，不能重复造 Task。所有必要字段仍受真实预算与字符限制，不能保证任意工具参数都装得下；原生 Pi 压缩产生的摘要不能冒充完整原文，只使用仍可核验的原记录。

直接相关契约是 Task §8（新建仅接纳本次未绑定触发消息，不重新归属历史；State 跨会话共享）、Recent Window §4/13（连续边界和 pending、失败恢复）、State §14（初始 Goal 与唯一提交点）。补入较早用户后可能形成非连续选集，现有单 boundary 不能完整表达这种冷启动范围；需要单独确定轻量定位/恢复方案。这里只建议流程，不提前新增字段、工具或启停标记。

### B. 如何识别阶段节点

| 触发情况 | 是否做收尾检查 | 不应误判的情况 |
|---|---|---|
| 用户明确要求完成某模块/阶段，Agent 准备交付其结果 | 是 | 只是运行了一条工具 |
| 一个有明确结果的调查/修复已完成，准备说明结论 | 是 | 只有猜想、脚本创建、测试尚未执行 |
| 关键证据推翻旧结论，或主要方案改变 | 立即检查，不必等阶段结束 | 普通重试、无认知变化 |
| 暂停、交接或被阻塞，需要保留下次继续所需信息 | 是，记录未完成/失败边界 | 不能把暂停写成任务成功 |
| Window 移出提醒 | 检查待移出内容中有无重要信息 | 不强制每批写记忆 |
| 简短问答或无新重要信息的普通轮次 | 无需写入 | 不强制每次最终回复增加 F/D |

### B. 两层验收

业务验收：以用户目标为准，列出可检查的结果和必要验证；已有明确标准直接使用，没有明确标准时自行采用与任务匹配的最小检查，核心边界不清才提问。必须观察真实工具结果，标明测试范围、失败与未验证内容；目标未达成就报告阻塞/未完成。

记忆验收依次检查：

1. 当前是否绑定正确 Task？开始持续实质任务而未绑定时创建；同目标续作不重复创建，短问答不强制创建。
2. 本阶段是否出现影响后续的约束、已验证根因/结果、决定、失败原因或关键转折？State 已准确包含则不重复写，没有则批量 state_append。旧事实被修正时使用 modify_fact；不新增 Plan/Hypothesis。
3. 每条认知是否保留必要范围/条件，且证据真正支持结论？引用存在不等于语义成立，助手猜测不能证明外部事实。
4. 工具是否实际提交成功？根据版本回执和紧接请求的 State 核对，失败/不确定则报告，幂等重试不得重复记。无需默认每次再调用 state_read 把全文读一遍。

建议确认后加入固定 Rule 的具体短指引：

> 开始需要持续上下文的实质任务时，先确认当前 Task；已有同一目标则继续，无有效绑定才创建。纯短问答不强制创建。
>
> 准备交付阶段结果、改变主要方案、暂停交接或处理窗口移出提醒时，检查是否产生影响后续的新认知。先依用户目标验证业务结果，再把尚未准确保存在 State 中的重要事实/决定批量提交；没有重要新增则不写。
>
> 只有实际工具成功结果才能支撑完成结论。记录必要的范围、失败和未验证项；收到写入成功回执并核对新 State 后再宣称记忆已保存。一次工具结束不自动等于阶段完成。

### B. 验收场景

- 修复模块且真实测试通过：业务正确，State 留存关键根因/修复结果及对应 T 证据；随后窗口移出和重启仍能据此继续。
- 测试失败后换方案：State 保留失败与决定，不能写测试通过，不能擅自降验收目标。
- 已有同目标 Task、重复交付或无认知变化：不创建重复 Task、不反复追加相同 F/D。
- 纯咨询问答、普通工具轮、等待用户澄清：不要求强制写记忆。
- 工具写入失败、重试、并发与窗口管理并存：不伪报保存、不重复提交，不借此改已有 Window 独立提交设计。

程序测试可以检查绑定、版本和落盘内容，模型的语义判断还需多场景真实 API 验证。此方案尚未加入运行时 Rule，也未增加自动检查或新 UI。
