# 原生 Pi 与 MemWeave：80 阶段长任务对照报告

日期：2026-10-26。测试对象：仓库提交 `dcfd5da` 打包的当前开发版本（包内版本号仍为 0.1.0），Pi 1.4.0，真实 `deepseek/deepseek-flash`，thinking=off。没有发布 npm，没有修改插件运行代码。

本次同一任务的两条执行轨迹均完成 **80/80、80/80 阶段**。两边都完成了审计程序、48 批报告和后续需求变更；数值结果和操作口径见下表。**不能据此认定插件任务质量优于原生 Pi**：严格报告比对仍有共同缺陷，而且两边让模型阅读原始记录的方式明显不同。

实际观察到：MemWeave 累计输入（含缓存）减少 **80.32%**，输出减少 **44.18%**，各阶段执行耗时之和减少 **42.79%**；但未缓存输入反而增至原生的约 **4.45倍**。这里比较的是当前产品的完整执行行为，**不是仅替换窗口算法的纯消融实验，更不是实际账单降幅**。

## 1. 到底做了什么任务

这是80轮预先固定的用户请求驱动的一项持续工程任务，不是一条prompt后完全无人干预跑到底；后续输入没有按评分结果定制。它是一个独立的、可编程的合成长任务：用 Node.js ESM 从空骨架开发离线订单账务审计器，持续完成 48 批审计报告。每批 80 条结构化事件，总计 3,840 条；包括收款、部分退款、重复投递、费用、拒付、异常金额、超窗退款和未来事件。金额均为合成数据。每条背景 note 重复度较高，本任务能检验长交互与口径维护，不能代表开放研究或复杂仓库修复的一般难度。

| 阶段 | 内容及事先确定的要求 |
|---|---|
|1–16|逐项实现 reconcile、金额校验、时间排序、幂等、退款、拒付、币种隔离、保留金、CSV、汇总及 CLI；公开累计用例逐步增加到31项。|
|17 / 43 / 70 / 76 / 80|交接追问：负责人、审批引用、备份天数、灰度渠道、发布授权、旧审批撤回原因、沙箱状态。|
|18–69中48个批次阶段|处理B001–B048，实际调用实现，输出结果与各批当时的审批/人员快照。|
|30|退款默认48h→72h；审批GATE_SABLE_17→GATE_OTTER_42；备份14→21天；旧报告不得用新口径回算。|
|56|只执行一次本地合成探针，返回passed=false/GW_SANDBOX_UNAVAILABLE；如实报告受阻和未验证范围。|
|65|探针配置恢复后实测；负责人MICA_73→LYNX_29，渠道pilot-5pct→pilot-2pct；真实发布仍未授权。|
|71–80|回归、48批汇总、幂等检查、README与最终交接。|

这不是此前定稿的 Harbor/公开 benchmark 实验系统的首版实现，也不改变其任务集或架构。此次是用户另行要求的一次临时补充诊断；任务材料、要求和评分器均放在系统临时目录运行。冻结输入与逐阶段脱敏证据随报告保留，临时执行代码及 Session 在复盘后删除。

## 2. 环境、对照条件和判分办法

- 两边使用同一个真实 DeepSeek 配置、同一 Pi 1.4.0 公开 SDK 的 AgentSession/原生 Agent Loop、完整默认 System Prompt 与 read/bash/edit/write 四个原生工具。插件侧加载冻结 npm 归档的生产 launcher、完整 Rule 和12个记忆工具；每次出站前校验，未用精简提示词、假模型或预填 assistant 历史。TUI按键、其他个人扩展/skills不在这次无界面隔离环境里。
- 原生自动压缩保留默认开启，reserveTokens=16384、keepRecentTokens=20000；插件按当前产品策略关闭自动压缩。公共 cacheWarming 关闭以排除后台推理，原生重试策略保留。N/B没有人为缩小，插件默认200/40；State 500条、正文100字符、整理批次100。
- Pi静态模型声明1,000,000上下文/384,000最大输出；插件正常核验提供方容量1,048,576，基础629,145、额外209,715、峰值预算838,860。插件出站输出上限62,914，原生为384,000。这是默认产品政策差异；上限与实际生成量分开记录。
- 同一80条用户请求、同一输入、同一阶段变更。奇数阶段原生先执行，偶数阶段插件先执行；允许两边自行维护代码、报告与文件笔记。每边独立 cwd/agentDir/Session/记忆目录，不交换对方产物。第43阶段后实际重建进程、从同一Session文件继续，不是只清空一个变量。
- 外部评分器在模型每阶段结束后检查只读材料哈希和累计公开测试，不把隐藏核对失败反馈给模型。每阶段重复累计测试只检验回归，不把重复次数当成独立样本。最终另测20个未公开数值/ID变体；这些变体源于公开功能，不是独立 benchmark。批次严格比较完整结构、金额、订单、ID、拒绝项顺序和当时口径。
- 同时保留补充诊断：仅忽略rejected数组顺序再比对，以区分算账错误与排序问题；此项不替代严格结果。交接自由文本中包含正确轮换标识也按语义认可，不要求措辞逐字一致；恢复后的available、passed=true等同义成功表述也认可，原逐字结果保留。

## 5. 具体问题、原因和建议

### 5.1 公开测试全通过，为什么48批严格比较仍失败？

两边的实现都先筛出字段不合法的事件，把错误立即放进rejected，再对有效事件排序、执行业务检查。结果“字段错误”总是先于“业务错误”输出。约定则要求整体按事件时间/原位置的处理顺序输出。这不会改变金额，却会让完整结果不符合协议。这是模型生成的临时业务程序的共同缺陷，MemWeave项目并不存在账务模块，不能把它写成插件源码的账务bug。

最小复现：输入先放一条1月2日的非法浮点capture，再放一条1月1日且无capture的refund。正确顺序应是refund的NO_CAPTURE在前，非法capture的INVALID_AMOUNT在后；两边实际相反。原先31个公开测试及20个数据变体没有混合这两类错误，因而未发现。

推荐：这种业务实现先把原始位置和可解析时间作为处理标识，在同一稳定时间序列中做字段与业务校验；新增一个混合错误顺序测试即可，不需要改记忆架构。此次没有修改测试中的交付代码，也没有把忽略顺序后的通过率冒充严格通过率。

### 5.2 插件早期把“旧文件”误当成撤回原因

第17阶段尚未发生审批撤回。插件却把“historical-note.txt是2025年旧记录”填入old_gate_withdrawal_reason；这只能说明文件年代，不能说明当前审批已撤回。原生返回null。第30阶段用户明确提供POLICY_ROTATION_30后，两边后续都能给出正确当前审批和撤回标识。

这是证据含义混淆，不是存储丢写。历史记录曾使用同一审批码，与当前用户重新确认该码可以并存。推荐先用这一案例评估“未知就保留null、旧文档不等于新事件”的既有执行规则；若改说明，应替换对应已有短句而非持续增加常驻提醒。本轮没有证据支持增加一个独立审查Agent或自动摘要。

### 5.3 配置状态和实测结果被混为一谈

第17/43阶段，两边都能从可见probe-status.json得知available=false，但此前未执行node probe.mjs。交接中却出现“探针实际输出GW_SANDBOX_UNAVAILABLE”的说法。故固定判它们“必须not_checked”也不合适：状态文件确实可读；真正有问题的是把读配置说成已运行验证。该项语义复核与原逐字评分均保留，不把修正测试口径当作产品能力进步。

第56阶段两边真正执行一次探针，正确报告passed=false、退出码0和未验证范围；第65阶段实际重跑后正确改为passed=true。本地探针只是合成fixture，不能外推真实网关连通或生产可发布。

推荐：将“观察到配置不可用”“已执行探针返回失败”“未验证真实环境”分别记录为有来源的认知。评估器按实际工具执行记录核对，允许没有执行时报告已知配置但不得声称实测。对通用插件不建议新增一套业务探针状态机；它应继续使用现有Fact/Decision及证据接口。

### 5.4 失败与恢复：当轮没保存，但后来补记了

插件第56阶段和第65阶段都正确回答，但这两轮没有state_append。复核全部State操作后可以确认：第58阶段将受阻结果及证据T247写成F50，第66阶段将恢复结果及证据T281/T282写成F59。准确问题是**分别延迟2轮、1轮后补记**，不能表述成最终没有保存，更没有证据表明存储丢写。

这两条认知在后续交接时已经处于State，因此不能把后续答对全部归功于Recent Window；同样，本次也没有做去除State的对照，不能确认答案究竟主要依靠哪一部分。

风险仅在尚未补记的间隙：若此时中断后进入不同上下文、切Task，或相关事件随后退出窗口而始终没补记，恢复可能缺少关键依据。这次没有实际观察到该风险导致遗忘。与现有[疑难case](DIFFICULT_CASES.md)相关，但不把用户未明确要求的每轮写入都当成硬性验收。

推荐优先明确何种交付必须持久保留（用户口径改变、受阻边界、有效验收），用现有工具检验，避免“每轮都写”和自动生成事实。此前未证实有效的额外提示不恢复。本次仅记录，不实施新的门禁、提示或额外模型调用。

### 5.5 Goal只覆盖了第一个子阶段，检索入口也没有实际使用

初始Goal为：`实现reconcile(events, options)基础capture聚合及规定返回结构，空输入返回零，运行check.mjs`。但用户开头的总目标还包括48批报告、变更和最终交付。此后没有update_goal；本次也未调用task_find，而是直接task_create。因此不能用这次单Task运行证明混合索引或跨Task恢复效果。

这次没有造成重复Task或最终口径错误，因为测试只有一个新Task；长期任务索引摘要却可能只反映“基础capture”。推荐在既有task_create说明中明确Goal表达整体目标、阶段结果写Fact，不把每阶段建新Task；首次检索遵循性另用有真实候选的固定case检验。先不扩大门禁或引入复杂工作流。

### 5.6 工具错误和多余核对

插件首次将task_create与bash放在同一批调用，bash被TASK_BINDING_REQUIRED拒绝，随后完成绑定重试；第15阶段state_append有一项漏type被拒绝。非法输入未落库，后续修正。原生也有脚本括号/引号、空grep结果等可恢复错误。两边工具错误详单在证据中；不能把所有非零退出都解释成产品损坏。

建议先保留现有严格拒绝和具体错误信息；初始化这种有依赖的步骤按已有顺序串行。原生逐批反复读取结构、做全目录哈希和多次结果核验增加了调用；可把同一阶段彼此独立的只读核对合并成一次命令。这是执行策略改进，不需要重写Agent Loop。

### 5.7 原生额外验证发现了一个插件侧未发现的数值边界问题

第73阶段原生主动验证大整数计算，并把fee/保留金乘法改成精确BigInt中间计算。以最终代码另做同样离线检查：单笔capture=9,007,199,254,740,991（JavaScript最大安全整数）、fee_bps=10000，应当全额计费，净额0。原生输出fee=9,007,199,254,740,991、净额0；插件侧生成的业务实现输出fee=9,007,199,254,740,990、净额1。

原因是金额本身虽然安全，乘以10000的中间值却超过安全整数范围；Math.floor(amount*bps/10000)已经受到浮点舍入影响。推荐仅在业务程序该处使用BigInt整数乘除后转换，不需要改MemWeave。这个检查是事后补充，不计入原冻结31+20用例；原参考实现也用了浮点乘法，因此本边界改用独立BigInt推导作裁判。计划内数据金额很小，原成绩不受这一oracle缺口影响。原生更充分的验证在这里有可见收益，不能把较多token全部视作浪费，也不能据本次结果断言插件质量更高。

## 6. 上下文管理究竟发生了什么

- 原生自动压缩事件数：**0**；插件：**0**。原生单次输入峰值685.54k，未触发默认自动压缩。因此这次没有检验“原生压缩导致遗忘”或“插件优于原生摘要”，不能做这种结论。
- 插件实际产生 **8** 个不同Window移出批次，候选规模见证据；默认200/40保持不变。80条用户请求不等于80个事件：每个用户消息是一个事件，每次assistant及其工具结果又是一个事件，所以此任务确实跨越窗口。
- 插件最终State：72个Fact、6个Decision，活动F/D 78，另有常驻Goal。远未到500，因此没有覆盖State满窗整理或State token准入极限。
- 预算快照的total包含输出预留、安全及协议等成本，不是提供方实际输入token；本报告分别保存预算和usage。Rule与预算在正常请求入口注入；原始Session仍保存交互，附加窗口元数据允许存在。

## 7. 为什么这次不能证明“算法本身省了这些token”

最明显的混杂因素：原生逐条向模型展示80条事件业务字段的批次为48/48，插件为0/48。原生多数批次把重复note归并为模板，全部note原文逐条可见仅1/48，插件0/48。两边代码均处理全量80条，但插件常只把字段概况与计算统计返给模型，原生逐条打印。按“先完整阅读原始事件”的严格模型可见解释，插件未完整遵循；按程序化审计目标，它又确实处理了全部数据。两种含义必须分开，不能事后把插件的更小可见负载当成同量阅读的算法优势。

还包括请求次数、输出详细程度、重复验证和自己写笔记的差异；原生使用文件笔记成功维持了变更，不能说“没有记忆工具就没有记忆”。模型没有固定随机种子，也未锁定供应商底层权重版本；缓存为供应商共享状态，不可清空；前置故障试跑也可能影响少量缓存。单任务单次成对轨迹只能描述本次结果，没有统计显著性或普遍优越性的证据。

推荐下一步：先选一个确实需要模型理解早期自然语言约束的长任务，把“程序处理全量数据”和“模型必须逐项阅读”分别写清验收；允许程序化处理时两边都允许，不把无关长note当作必要推理材料。公开benchmark按已定稿实验设计单独实现，不用此次分数代替。

另有两类问题应分开看。两边生成业务代码的错误顺序缺陷和插件侧业务代码的大整数误差，应补业务验收和修业务实现，不能把账务逻辑写入MemWeave。两边的阅读方式、验证深度不同，则是任务遵循与评测可比性问题：程序处理全部数据不代表模型逐项审阅，但允许程序化审计时不应把它一律当成偷工减料。

State能保存认知，不自动判断认知是否正确。比如D2记录了先格式校验、再时间排序执行业务的实现选择；这种两阶段方案本身可以正确，但当前实现没保证混合错误的最终排序。记录Decision或通过已有测试，都不能替代对用户要求的核验。本次也不能证明这个Decision导致了错误，因为原生同样犯了该排序错误。

改进顺序建议：先处理Task入口和整体Goal的遵循性，再核验重要变化的保存时机与粒度；工具误用继续依靠现有严格校验。暂不引入额外Agent、自动事实生成、全局新门禁或更长的常驻提示。
