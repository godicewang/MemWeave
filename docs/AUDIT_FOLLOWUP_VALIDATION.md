# 审计后增量改进与验收（2026-10-23）

## 目的、范围和实际影响

用户已确认：完整回读后按逐条真实消息计数，达到 10 条时恢复普通截断；历史 F/D 由 state_read 显式查询，最多 50 项，默认 8000/上限 50000 字符。先在提交 `30241f0` 更新直接相关规范与两份 Rule，再实现代码。

回读保护现在能跨用户插话和多个请求存续，减少刚读完原文就丢失的情况。代价是期限内可能重复发送更多文本或图片；完整内容仍占半额预算，放不下则取消。它不把已移出 Recent Window 的结果固定在上下文中，也不重新计算或延长旧结果的期限。

历史查询返回原正文、证据解释和归档/活动状态，解决当前认知引用旧 F/D 却无法查证的问题。旧 `{task_id}` 查询仍返回当前 State，memory_read 仍只负责 U/A/T/R。没有新增工具、State 事件、Pi custom 类型或数据文件，没有修改 Task 切换、窗口提交或原生 Session 消息。

预算估算/超限恢复、反复处理全部历史的性能优化仅作解释，本轮没有实施。既有强制 system 覆盖不兼容、其他 Pi 版本及未验收组合的边界保持。

## 实现与技术细节

- `src/state/read.ts`：历史查询 schema、纯读取/字符分配、实际结果范围核验；从完整 State 重放结果读取，包括已移出和已归档条目。
- `src/task/service.ts` 与 `src/extension/register.ts`：受 Task 锁保护的只读接口及既有 memweave_read 范围标记。查询不更换当前 Task，不分配 R；重复 ID 按输入顺序处理，缺失/截断逐项说明。
- `src/window/read-grant.ts`：从当前分支最后 10 条原生 user/assistant/toolResult 消息推导年龄，保护实际且可核验的回读结果；第 10 条后续消息到来时失效。错误/中断 assistant 若已保存也计数；Rule、State、提醒、system 和 custom 元数据不计。
- 不增加持久化倒计时；重开、fork/tree 依据所在祖先链恢复。再次回读有自己的新期限，不重置旧结果；供应商内部重试沿用请求快照。
- 两份规范 Rule 正文及生成资源逐字一致。升级 Package 不覆盖用户的运行时 rule.md，指南说明备份后合并新增协议。

### 真实 API 发现的 Schema 问题

本地 TypeBox 校验和 Faux 接受最外层 Union，但 DeepSeek 返回 400：工具参数 Schema 必须有 `type: object`。新增 state_read 首先暴露该问题；开启默认全部 11 个工具后，确认既有 task_resume 也存在相同问题，此前部分工具 loadout 未覆盖它。

修正仅为 Union 增加 object 根结构和属性声明，保留原有分支校验；task_resume 仍严格二选一，state_read 仍拒绝无 event_ids 的 max_total_chars、未知字段与超限值。没有扩大参数契约。单测核对最终 JSON Schema 的 object 根，新增真实测试保持默认 11 个工具全部启用。

### 失败记录与清理

初次真实整组中，3 项在工具执行前因 state_read 的 Schema 400 失败；默认全部工具复核又发现 task_resume 同因失败。修正后历史查询及原有 Goal/State 流程通过。400 请求不计为成功推理或业务闭环。

最终整组的跨 Task 图片识别预期 `18827307`，模型返回 `18827607`，一个数字错误；其前置图片引用、无答案泄漏、工具成功、图片字节与出站哈希断言已通过。未调整 OCR 断言或修改生产图片处理；单独复测通过仍不构成 OCR 准确率保证。

早期回归有两项仍断言旧的一次性保护，已按批准的新期限更新；磁盘重开比较改为核对 JSON 可持久化字段，避免把未持久化的 undefined 属性误判为原始消息变化。原始消息和 State 字节不变的断言继续保留。

临时 Session、运行数据、安装 checkout、归档、缓存和故障夹具通过 after/finally 清理，包括失败测试；没有向 npm 公网发布、创建 release/tag 或改动用户认证。

## 两个数字与尚未改动的问题

**567,793 是当前字节估算器的结果，不能当成模型实测 token。** 构造的压力样例有 1800 条 Fact，每条 100 个常见汉字：正文 UTF-8 字节为 `1800 × 100 × 3 = 540000`，加编号、证据与 State 呈现格式 27793，得到 567793。该样例已重新复现。模型精确容量 1048576 的一半为 524288；程序将保守估算的成本与此上限比较，可能提前拒绝。这里不是用户现有 State 的统计。

仍有恢复缺口：State 不允许裁剪，但未满默认 2000 条时不会准备满窗管理批次；若完整 State 先超预算，主 Agent 请求会被取消，不能靠这次调用清理自己，重启也不改变这一点。后续需讨论更准确的计数和安全恢复方式，不能因本次查询/生命周期改进就声称已修复。

**166 是压力测试中当次选中的近期消息数，不是新配置或 166 轮对话。** 默认窗口仍为 200 个交互事件、每批移出 40 个；实际消息数随事件内容和滑动时机变化，assistant 与多个工具结果只算一个事件但包含多条消息。

序列化是把内存对象转成 JSON 文本，例如 `{role:"user",content:"你好"}` 转成 `{"role":"user","content":"你好"}`。现有来源核验对原生历史、有效投影及传入消息重复执行该转换；即便最后只发 166 条，也可能先处理全部旧历史。审计的 1000 条样例中约 3000 次转换、约 12.5 MB 本地文本处理，不表示将这些额外文字都发给模型。

建议后续保留来源验证，将已校验的记录/指纹缓存，只处理新增或变化部分，并为磁盘变化、分支切换等建立失效规则。这是尚待确认的优化方向，本轮没有新增缓存或改变验证机制。
