**后续状态：** 本文保留修复前的真实审计记录。用户随后确认采用原生呈现、仅显示上次成功请求实际用量，已在 `4ac3e74` 完成修复与复测；当前行为、范围和证据见 [修复验收](CONTEXT_DISPLAY_VALIDATION.md)。下文“当前／尚未修复”均指本次历史审计候选。

**结论：当前原生 Pi 状态栏不能作为 MemWeave 本次请求上下文的实时准确显示。最终回复完成后的 token 总量与 API 一致，但执行中可能显著高估或低估；百分比的容量分母也与已核验容量不一致。确认两项需要修复的显示问题，均尚未修改实现。实际发送限额、缓存计数和窗口裁剪没有发现错误。**

本轮只测试、记录和提出修复方向，没有改 Pi 核心、MemWeave 业务代码、固定规范、界面行为或发布版本。

## 环境和方法

- 候选 `048e1765f3208fbf63d02da662e60da16d294860`；本机实际 `/opt/homebrew/bin/pi`，Pi 1.4.0、Node v23.11.0。加载日常使用的开发仓库 Pi Package，不使用 npm 公网旧归档代替当前代码。
- 三档主测试采用日常默认 `deepseek-v4-pro`；另补 `deepseek-flash` 的实际 60 万 token 以上输入，验证真正的大请求。两者由插件在请求中核验的容量均为 1,048,576 token，原生状态栏内部采用 1,000,000。另只读核对日常配置的 models-store.json：两个模型也均为 1,000,000，且没有 models.json 覆盖，与隔离实测一致。
- 全部实测在真正的 CLI TUI 中执行，PTY 为 50 行、190 列，实际选择“启用 MemWeave”并原生 reload；新临时配置另经过首次初始化确认，已初始化者按原流程保留。屏幕持续显示“MemWeave 已启用”。没有用假 UI、Faux 模型或本机 HTTP 替身替代这些推理请求。
- 使用临时 HOME、agentDir、cwd 和 Session；认证只通过仓库外私有 auth.json 的链接复用。真实全局的默认模型、Package 设置和压缩值保留。临时配置关闭压缩、缓存预热及重试，关闭无关 MCP/skills；--offline 固定启动目录、不进行启动更新，API 推理与插件容量核验仍真实联网。
- 历史负荷由原生 SessionManager 写入合成 user、assistant/tool-call、tool-result 配对，历史 usage 为零；这些是计量夹具，不声称历史工具真的执行过。实时推理、窗口设置调用和上下文组装均使用实际 Pi 与 DeepSeek。没有对业务项目执行夹具里的写文件操作。
- 观测扩展只读取事件，按 Package 顺序放在 MemWeave **之后**。在最终 context_with_system 读取预算，在 before_provider_request 读取实际 payload 形状/输出上限，在 provider_stream_event 读取服务器原始 usage，再对照 turn_end、agent_end 的规范化 usage 和 ctx.getContextUsage()。PTY 同时采集真正的状态栏百分比。

有效证据共 **8 次真实推理**：低 2、中 2、高 Pro 3、高 Flash 1；另有仪器顺序校准期间的 2 次低负荷请求，未混入下表。最初使用显式 -e 加载观测扩展时，它先于 Package 执行，看到的是变换前视图/输出字段；修正为尾置观测并核对预算、输出上限后才采纳正式结果。这是测量方法修正，不是产品输出上限错误。

合成负荷为低 9 条消息/5 个事件、中 201 条/101 个事件、高 Pro 581 条/291 个事件。中档原正文约 1.28 MB、不可裁剪参数约 184 kB；高 Pro 原正文约 4.01 MB、参数约 502 kB。主测试的插件总预算占模型容量约 12%/50%/70%，覆盖低中高预算压力；Pro 的保守计量不等于实际 API token，因此另外增加了真正大输入的 Flash 档。

## 真实读数

`k=1000 token`。正确比例采用 **API 的 input+output 总量 / 1,048,576**，与原生 Pi 当前“上下文 token”的含义保持一致；不把输出预留或安全池加进实际已用。

| 场景（首请求） | 执行中原生显示 | API 输入 / 输出 | 正确容量占比 | 完成后原生显示 |
|---|---:|---:|---:|---:|
| 低 Pro | 0.4% | 8,929 / 5 | 0.8520% | 0.9% |
| 中 Pro | 36.9% | 282,405 / 6 | 26.9328% | 28.2% |
| 高 Pro | 113.2% | 409,811 / 5 | 39.0831% | 41.0% |
| 高压 Flash | 42.2% | 662,235 / 7 | 63.1563% | 66.2% |

以上执行中数值同时在原生 getter 和实际 PTY 状态栏序列中出现；完成后的原生 token 总数分别为 8,934、282,411、409,816、662,242，逐个等于服务器 API total_tokens。

高 Pro 随后由真实模型调用一次 `recent_window_set({turns:20,evict_turns:4})`。工具续跑时，实际请求已从 N/B=200/40 改为 20/4：

| 工具续跑阶段 | 原生显示/估计 | 新请求实际 API 用量 |
|---|---:|---:|
| 新请求发送时 | 41.1%，411,107 token | 输入 86,957，输出 9，正确占比 8.2937% |
| 新请求完成后 | 8.7%，86,966 token | token 数与 API 一致，百分比仍使用原生分母 |

41.1% 来自上次 API usage 加尾部工具结果估计，并不是本次已缩小后的请求大小。因此偏差不仅发生于首次恢复，也可出现在正常执行中的工具续跑。

## 确认需要修复的两项

| 问题 | 证据与影响 | 状态和修复方向 |
|---|---|---|
| 执行中显示没有对齐请求变换后的上下文 | 高 Pro 显示 113.2% 而实际约 39.1%；Flash 显示 42.2% 而实际约 63.2%；缩窗后仍沿用约 41.1% 而新请求仅约 8.3%。可明显误导是否接近容量、窗口是否生效的判断 | **已确认，未修复。** MemWeave 的请求展示应区分发送前“预计/保守上界”和响应后“API 实际”；使用同一请求快照。不能把原始 Session 或旧 usage 当作当前请求，也不能为修显示将临时 Rule/State/预算写入 Session |
| 百分比的容量口径与插件不一致 | 原生 ctx.getContextUsage().contextWindow=1,000,000；插件核验为 1,048,576。完成后 token 正确，比例相对真实容量占比高估 4.8576%；例如 Flash 的 66.2% 实际约 63.2% | **已确认，未修复。** MemWeave 展示应使用本请求已核验容量，或明确标出所用容量口径；不通过 patch Pi、修改 SDK 或静默改全局模型目录解决 |

两项都是当前启用组合下的显示问题；没有证据表明其导致了本轮请求超发或丢失历史。下一步具体采用新增状态、原生自定义 footer 或其他公开展示方式，需要按 AGENTS.md 先对齐外部显示契约，本轮不擅自实现。

这里确认的是原生配置容量和提供方核验容量不同，并未确认 1,000,000 是目录陈旧、取整还是有意保守设置。按原生配置计算本身数学上正确；需要修复的是 MemWeave 场景下的显示一致性和解释，不能据此直接宣称 Pi 的通用计算公式有 bug。

原生路径依据为 FooterComponent.getSessionStats()/render() → AgentSession.getContextUsage() → estimateProjectedContextTokens()/calculateContextTokens()：缺少有效 usage 时估算原生投影；有 usage 时使用最近一次真实 usage，加其后消息的估计。它不执行 MemWeave 的请求级变换。原生 footer 使用 limits model 的静态 contextWindow 计算百分比。

## 没有发现错误或属于预期的部分

- 每个服务器 prompt_tokens 均等于规范化 usage.input+cacheRead+cacheWrite；没有漏算或重复计算缓存。最终无尾部消息的原生 context tokens 等于 API total_tokens。工具轮之后的 getter 可能另含尾部结果估计，不能误当成该次 API 的原始 total。
- `↑/↓/R/W` 是会话累计消耗，不是本次上下文大小。例如中档两次调用后累计非缓存输入约 564k，但当前上下文约 282k，这是正常口径差异。
- 每个出站输出上限都为 62,914，等于同帧预算 O。每次真实 API 输入加最大输出预留 O、基础安全 A 均不超过 838,860；未发现未预算的超限发送。
- Flash 高压请求的必需成本 K=716,427，确实超过基础 629,145，使用了已允许的额外额度；普通 Window=48,572/48,973，回读池闲置未借给普通 Window。实测输入 662,235 + O 62,914 + A 31,457 = 756,606，仍低于 838,860。
- Flash 本地输入上界为 670,628，实际 API 输入为 662,235，保守差额约 1.27%。Pro 明确使用 utf8-bytes-with-protocol-margin，不能将其预算数字当作精准实际 token；改进 Pro tokenizer 匹配是可选优化，须先核验，当前不归类为算错。
- 中/高普通正文实际发生截断；高 Pro 首轮临时可见 292 个事件是既定待移出提醒机制，之后提交边界；缩窗确实生效。原始夹具消息保留，没有 compaction/context_edit，没有把临时预算正文持久化。

## 证据、复现与范围

去敏的 [机器读数](../发布测试/执行记录/数据/2026-10-25_上下文显示.json) 保存每个请求的实际 API usage、规范化 usage、预算、payload 计数和真正的 TUI 百分比序列，不含密钥、请求正文、业务数据或 Session 副本。
