# 澄清工具与绑定检查调整验收

2026-10-26。用户确认：增加Agent可调用的澄清工具；删除task_find的initialize参数；创建/恢复调用表达绑定意图，失败且仍未绑定时才纠正，搜索不触发门禁。先同步直接规范，再写边界测试并实现。本轮不发布npm、不更新本机日常安装，不修改暂缓的记忆形成、State错误修正或两类窗口提醒。

## 第一部分：两个原测试结果到底是什么意思

### “正确澄清被纠正，随后猜选任务”

旧E4同时存在三个合理候选：支付重复扣款、退款超时、支付对账。用户只说“继续之前支付那个任务”，不足以选中其中一个。Agent先搜索，第一份回答已经正确问用户要继续哪个。旧逻辑却把搜索时的initialize=true视为必须完成绑定；将这份提问当作“未绑定失败”，在没有新用户选择时强制模型再试，最后模型猜选了一个Task。

所以失败在“还没得到用户选择就进入了Task”，不是检索没找到候选，也不是用户答错。没有观察到删代码或改坏State；当时空工作区是测试夹具本来就为空，不是恢复丢了文件。

### “业务处理3/3，阻塞认知1/3”

这是三个独立样本，每个都把配置改到策略目标，并真实执行了一次固定失败探针。三个都如实说明了EHOSTUNREACH与未验收范围，所以“处理阻塞合格”是3/3；**探针本身三次都没通过，并不表示端到端验收3/3通过**。

| 原案例 | 长期保存结果 |
|---|---|
| C1 | 有Task，但只有最初的Goal，没调用state_append，未保存执行后的失败边界 |
| C2 | 保存2F+1D，含配置已改、探针passed=false、具体原因、不绕过/不重试的决定 |
| C3 | 未建立Task，也未写State；仅有原生Session中的完整过程 |

因此“1/3”表示只有一个样本把失败边界保存进长期State。它不是完成进度，也不是另两个的原始聊天被删除。按用户要求，具体证据与未验证建议移入[疑难case](DIFFICULT_CASES.md)，本轮不追加收尾状态提示或自动生成认知。

## 第二部分：本轮实际改动

### 新增 task_clarify({question})

- question必填且非空，未绑定/已绑定都可调用；不创建Task、不改Goal/State，不将Task状态改为paused。
- 只问缺失后会阻止**当前这一步**的信息。仅登记已经明确的Goal，不要求未来实现细节；避免引入澄清工具后反而阻碍简单的目标登记。
- 使用原生工具terminate提示结束自动续跑。有对话UI时调用Pi原生input；非空的实际用户答复通过sendUserMessage followUp进入新的真实user消息，不展开slash模板。取消、空白或无UI时展示问题，本轮停止，等待下一条输入。
- 必须单独一批调用。若与业务工具或第二个澄清调用混用，整批在执行前拒绝，不能边提问边操作；嵌套交互旁路明确拒绝。
- 不新增暂停custom、数据库、第二套Session或独立模型。问题/工具结果及真实答复按原生消息和既有事件规则保存。

### 删除 initialize，并保留历史可读

FindSchema只剩query/keywords/limit。新调用带旧字段严格拒绝；task_find只发现，不切换或触发绑定限制。当前输入实际调用task_create/task_resume才表达绑定意图，成功以既有scope为准；失败且仍未绑定时才限制业务并有界纠正。没有进入Task的漏判仍属于已暂缓问题，不宣称程序能识别所有有意义输入。

正常澄清不触发纠正。不能只看assistant的stopReason：部分工具调用消息也可带stop。程序核对单独的task_clarify调用、实际非错误工具结果、调用ID及question/status一致后，认可本轮正常等待。

memweave.task.binding.v1的字段、固定回执正文和来源核验保留。旧initialize只在读取既有失败回执时用于识别原来源，不能启动新门禁；不重写旧调用或历史。实际旧代码0a43fa6生成的两条回执已由新代码从磁盘打开并继续短问答，原文件字节前缀不变。

### 修改位置与规范

实现集中在src/extension/clarify.ts、src/task/model.ts、src/task/binding.ts、工具注册与TaskService.find；冷启动提示移除旧参数指引。State reducer/存储、两种窗口管理提醒、预算公式和恢复格式没有改动。

先增量同步Task §12/澄清工具、Rule两份正文、State §24及Window §20，更新架构、联合接线方案和用户说明，再实现。两份固定Rule模板与resources/rule.md已提取逐字比较（只允许文件末尾换行差异），一致。

### 首轮失败如何处理

首轮完整28项真实专项为25通过、3失败，全部保留在[脱敏验收数据](evaluations/2026-10-26-task-clarification.json)：

1. 旧restart澄清测试要求最后一定是assistant文本。新协议是成功的task_clarify等待结果；改为核对非错误工具结果及waiting_for_user，不放宽“未绑定、未建占位Goal”的标准。
2. 只登记明确Goal的真实样本过度追问未来实施细节。只收窄新澄清工具/现有Rule的适用范围，没有加分类器、工作流或额外模型；相同原输入复测及后续当前专项均通过。
3. npm产物恢复后新增GATE_artifact-live未满足最后Fact断言。按用户要求记录MW-004，未改记忆实现、未重采为通过。该次输出不足以区分未追加/正文不符等路径，不编造唯一原因。

随后当前候选复测明确过滤第3项，27个具体验收通过。Node把被过滤后没有可执行测试的release.test.ts文件另统计为一个“通过”，所以runner显示28；它不是业务案例，数据和本报告都将其剔除。**不能用这个数字宣称全部28项或完整发布验收通过。**

275项中的启动测试预期工具数由11改12，正式出站工具守卫也要求新澄清工具存在，未缩减工具或提示。边界测试先在旧实现失败，补实现时还发现stopReason不能代表澄清结束，修正为原生调用/结果核验后14项通过。
