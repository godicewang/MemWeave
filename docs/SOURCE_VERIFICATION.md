# 来源核验优化（2026-10-24 用户确认）

## 一、目的、范围与取舍

采用有界来源定位缓存、直接比较消息、按需调用 Pi 原生投影。取消来源核验中的整条消息 JSON 序列化及字符串集合，减少重复计算和临时字符串分配。缓存只帮助找到原件；每次收到 Pi 复制的新消息仍检查完整内容，不能把上次通过的结论当作本次通过。

长期缓存最多 8192 个定位项、约 16 MiB 预算，超限淘汰最久未使用项。只存有长度限制的定位键、Pi entry ID、快照数组位置和估算开销，不保存正文、图片、对象副本或投影。新增磁盘占用为 0。缓存命中后重新确认当前位置的 entry ID，并与本次快照中的当前原件比较；miss 集中扫描，不逐条重扫全部来源。

范围限于来源核验及必要的生命周期清理。不改 Window 选取/预算/计数、State、回读授权、持久化协议、工具或扩展兼容范围；固定 Rule 正文不变。依旧不支持的表示沿用 UNSUPPORTED_WINDOW_CONTEXT 并主动取消。保留 Pi 唯一原始历史，不建立消息镜像、磁盘缓存、摘要或另一套原生投影实现。

内存限制针对新增长期缓存数据，包含保守的索引结构开销估算，不是整个 Node/Pi RSS 上限。请求中的临时索引与 Pi 本身的历史仍随输入量变化，在请求结束或异常后释放。核验仍需遍历传入历史并检查内容，不承诺只处理新增部分，也不承诺整个请求获得微型测试的加速比。

## 二、实现与验收边界

### 定位、比较与投影

- role、timestamp、toolCallId 等小字段构成有长度限制的查找键。键允许碰撞，不能作为内容相等的证据；比较包含正文、嵌套参数、签名、图片和其他字段，数组顺序保留。
- LRU 按原生 entry ID 记录位置和键，使用当前请求的 entries[index] 再确认 ID。每条消息的缓存探测限定一个候选，避免大量同键时每次 miss 都扫描整片缓存。
- 所有 miss 先收集，单次扫描当前快照，为相关键构建临时候选索引；按内容匹配，常规消息顺序可复用候选游标。同键的其他候选仍可回退比较，不能因碰撞、输入重排或重复而误判。
- 仅剩余无法匹配普通原件的消息触发一次 buildSessionProjection()，按原生 sourceEntry/messages 核验；不复刻 context_edit/compaction 算法，不跨请求缓存投影结果。无匹配消息仍由原有诊断路径取消；system 和可接受的 compactionSummary 的既有边界不变。
- 当前请求的匹配结果只是局部布尔列表，不保存到长期缓存；失败也不遗留消息/投影引用。

### 上限与失效

定位键最多 256 个 UTF-16 code units，长期存储的 entry ID 最多 128；过长 ID 仍可核验但不缓存。每项按 512 + 4*(键长度+ID长度) 字节保守估算索引开销，8192 项与 16 MiB 两个上限同时生效。所有淘汰同时清理键索引，不保留历史空桶。测试可缩小内部上限，不新增用户配置字段。

缓存只属于一个 WindowService。Session 身份变化或当前快照不再包含上次末尾相同位置/ID 时清空；Pi session_start（包括 reload/new/resume/fork）及既有 session_tree handler 显式清理。正常 append 不全量失效，位置异常则重新定位。即使条目原地修改、ID/时间戳未变，命中后完整比较仍会发现变化。实例销毁后无全局缓存持有消息。

### 验收计划

先测试再实现：复制对象、正文/参数/签名/图片被改、同键碰撞与重排/重复、缓存内容变化、原生投影调用次数与变化、未知表示取消、LRU/字节上限及空桶清理、超过 8192 条历史、分支/Session/reload、原始数据不变和无需序列化。运行完整单测/类型/Pi 集成及相关真实 DeepSeek 闭环；临时性能与 GC/堆占用试验放系统临时目录，不将合成指标冒充全流程提速。检查 npm 包与固定 Git 提交安装，按里程碑提交推送。
