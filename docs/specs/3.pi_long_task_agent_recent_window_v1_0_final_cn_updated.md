## 1. 定位与核心取舍

**长期认知靠 State，短期现场靠 Recent Window，完整经历靠 Pi Session。**

Recent Window 不是第二套记忆数据库，而是每次请求时，从 Pi 历史中选出的有界消息视图。

本版确定：

- 关闭原生自动 compaction，不生成历史摘要，也不将摘要作为溢出兜底。
- 按完整交互事件滑动窗口，满窗后成批移出；模型可以调整窗口大小。
- Agent 总预算为实际模型最大上下文的 60%；Recent Window 缺省按模型计算 N/B，1M 档为 200/40，已有显式配置优先。
- 普通可展示文字统一采用单条预算截断：引用在前，截断标记在后。
- 图片、文件二进制块默认返回原件引用；必要的协议字段完整保留。
- 物理请求顺序为 **Rule → Recent Window（必要时临时包含待移出批次）→ 临时窗口提醒（仅待处理时）→ State 与预算快照**。State 在末尾作为独立 `user` 承载消息；提醒是请求级临时消息，不属于持久化历史。
- 不新增第四部分操作日志；状态更新和窗口设置的工具调用及极简结果正常保留在 Recent Window。

窗口退出和正文截断都只改变本次模型可见内容，不删除原始记录。需要长期保留的认知仍由 Agent 通过已定稿的 State 工具维护。

## 2. Pi 原生接入与复用

### 2.1 请求链路

Pi 的原生请求准备和 `transformContext` 保留；扩展 runner 先处理普通 `context` 并恢复 system/工具，再处理完整视图 `context_with_system`，之后仍由 Pi 转换、规范化和适配供应商。本项目只在一个完整视图处理器中先完成 Rule，再执行 Window/State。[S1][S2][S3]

| 接口 | 原生职责 | 本项目的使用方式 |
|---|---|---|
| `transformContext` / `context` | 原生消息变换；普通 context 不包含 system | 保留原生链，不在这里按旧 Rule 预先计算 Window 预算 |
| `context_with_system` | 每次模型请求的完整视图，包含 system/工具声明 | 同一快照中渲染 Rule，再调用既有四个 Window 函数，保留一个有效 system 头 |
| `convertToLlm` | Pi 消息转换为模型接口层消息 | 保留原生实现；利用 `custom → user` 转换 State |
| `SessionManager` | 保存会话、读取当前分支和原始记录 | 提供历史与恢复依据，不另建消息库 |
| `context_edit` | 持久记录历史消息的可见内容编辑 | 本扩展不使用它实现日常窗口滑动；区分 Pi 自身恢复记录 |

Window 四函数处理非 system 消息；实际渲染后的有效 system/工具成本计入 R。不能将整个请求拼成字符串，也不能在四函数执行后再补写 Rule。后置强制提示/工具投影及第三方变换按真实请求验收，不能仅凭注册顺序宣称全部兼容。[S3][S4]

### 2.2 停用压缩及已接受的副作用

用户明确在 Pi 配置中设置以下值，优先合并进受信任项目的 `.pi/settings.json`，也可选择全局作用域；它不是 MemWeave `config.json` 的字段：

```json
{"compaction": {"enabled": false}}
```

读取配置后，同作用域其他 Pi 也会关闭自动压缩，禁用/卸载本扩展不自动恢复。项目值可覆盖全局值，必须通过 `pi.getSettings()` 检查实际生效值；Session 启动/恢复及每次请求都检查，不静默写用户全局配置。修改设置后按 Pi 原生方式 reload/重启，不承诺已运行进程立即同步。[S6][S13]

仍通过 `session_before_compact` 取消手动压缩，并排除未经验证的自动整理扩展。取消 hook 不是关闭整个恢复流程：用户运行中重新开启压缩时，overflow/length 路径可能先追加 `context_edit`，再触发取消。用户已接受此边界；不保证有效会话视图绝对未变，不删除原生恢复记录，也不将其误作新 State 证据。[S6]

本扩展仍不使用 `firstKeptEntryId`、`findCutPoint()` 或 compaction entry 管理窗口；不生成历史摘要兜底。预算不可满足或有效压缩设置不符合要求时，主动取消当前请求并报告。此取消机制针对正常主会话链路，不覆盖其他扩展自行发起的调用；详细共享设置/版本/共存约束见 `../PACKAGING.md`。

### 2.3 Rule 与工具定义的位置

逻辑预算中，Rule 包含有效系统提示、记忆协议、工具定义及已向模型声明的 MCP 能力。

物理请求中，系统提示与工具定义仍由 Pi 和供应商适配器分别编码。不要把工具 schema 再手工复制一份进提示词；MCP 连接配置也不等于全部需要发送给模型的内容。[S2][S7]

## 3. 文件与运行时状态

```text
Pi 原生会话位置（由 SessionManager 获取）
└── <session>.jsonl
    ├── 原始 user / assistant / tool 记录
    └── 扩展 custom 记录：窗口设置和必要恢复定位

~/.pi/memory/
├── rule.md                         既有记忆规则，增加 Window 使用协议
├── config.json                     既有配置，保存窗口默认参数
├── index.json                      已定稿的全局 Task 索引
├── <cwd_key>/tasks/<task_id>/
│   ├── state.json                  已定稿的 State 演化记录
│   └── state.md                    已定稿的当前 State 呈现
└── blobs/<content_hash>            按需保存长期可回读原件
```

**不新增 `recent.json`、独立 Window 消息文件或操作日志文件。** `blobs/` 只是完整原件的补充，不重复保存已有可靠来源的小消息。

窗口参数和选取起点属于当前 Session／分支的显示状态，不写入共享的全局 `current_task`。少量恢复元信息可写入 Pi 的 `custom` 条目；该类条目不会自动进入模型上下文。[S5]

正常运行使用 Pi 已加载的历史和增量边界；重启、分支切换或扩大范围时从原始 Session 恢复。不每轮重新扫描磁盘，也不修改 Pi 保存的原始消息对象。

## 4. 窗口单位、滑动与恢复

### 4.1 两种计数不得混淆

**交互事件按以下两种单位计数：**

- 每条真实用户消息，单独算一个交互事件。
- 一次 assistant 返回及其触发的全部工具结果，合起来算一个交互事件；没有工具调用的 assistant 返回也算一个事件。

工具结果不再单独增加事件数。所有消息保留原始顺序；程序注入的 State 不是用户发言，不参与计数。

```text
事件 101：U12
事件 102：A31 → T51、T52
事件 103：U13
事件 104：A32
```

上述四个事件包含六条实际消息。窗口容量 N 按事件计数；第 5 节预算分母 M 按本次选中的实际消息数计数。

用户事件通过原始用户消息识别；assistant 事件可利用 Pi 的 `turn_end` 提供的 assistant、工具结果及 entry ID 建立边界。重试同一次请求不重复滑动；工具调用和对应结果不拆开移除。[S13]

### 4.2 成批滑动

窗口设置包含：

| 参数 | 类型 | 含义 |
|---|---|---|
| `recent_turns` | 正整数 | 最多保留 N 个完整交互事件，省略时按模型预算计算，最大默认 N=200 |
| `evict_turns` | 正整数 | 满窗后每次移出 B 个完整事件，省略时 ceil(N/5)，最大默认 B=40，要求 `1 ≤ B ≤ N` |

以 1M 档默认 N=200/B=40 为例，已有 200 个事件、再加入第 201 个事件时，本批移出最早 40 个。仅计这一个新事件，移出后的逻辑窗口为后 160 个旧事件加新事件，共 161 个；提醒期间新增的其他完整事件仍按同一规则计数，未再次超限前不提前移出下一批。待移出内容在提醒请求中的临时保留仍遵循下述两阶段规则。

以下小窗口示例采用 `N=5、B=2`，仅用于说明行为，不是默认配置：

```text
已有事件：101 102 103 104 105
新增 106：先移出 101、102，得到 103 104 105 106
新增 107：得到 103 104 105 106 107
新增 108：移出 103、104，得到 105 106 107 108
```

不足上限时不提前移动；需要加入新事件且会超过上限时，按 B 移出。真实用户消息进入当前会话后即作为一个独立用户事件参与窗口计算；assistant 事件则须在该次 assistant 返回及其关联工具结果完整确定后才作为一个完整事件参与窗口计算，不得在工具结果尚未齐备时拆分移出。若一次恢复带来多个事件，则按相同规则处理至满足 N。单纯重新组装同一批历史不得推进边界。

#### 待移出提醒（临时上下文）

窗口即将移动时，采用两阶段处理：

1. **待处理阶段：**程序确定本批最早 B 个完整交互事件及移出边界，并为本批分配稳定的 `batch_id`。为让模型有机会检查这些内容，本次请求临时保留待移出批次，即使可见事件数暂时超过逻辑容量 N；并在请求末尾附加一次短提醒，例如：“U12 之前的交互事件将退出 Recent Window。如有影响后续任务的重要认知，请使用 `state_append` 保存；否则按窗口规则移出，原始记录仍可通过历史回读找回。”
2. **提交阶段：**待该 assistant 返回及其关联的全部工具调用均已完成后，程序按 `batch_id` 提交滑动，并通过 Pi 现有的扩展 `custom` 记录／会话元数据持久化新的窗口边界；该边界更新成功即为 Recent Window 的提交点。提交后续请求不再注入该提醒。若请求未完成或边界提交失败，保留同一待处理批次，不重复推进边界。`state_append` 是否成功与 Recent Window 的提交彼此独立；原始 Session 仍保存所有历史，因此 State 写入失败不自动阻止 Recent Window 按自身批次提交。

提醒是本次上下文的临时消息，不写入 Pi Session，不分配 U/A/T 编号，不属于真实用户输入，也不参与 N/M 事件计数。每次窗口滑动并不要求模型都调用 `state_append`；只有存在对后续任务仍有重要价值的认知时才主动保存，没有值得保存的内容时无需调用。State 写入与 Recent Window 批次提交彼此独立：`state_append` 失败不能被当作写入成功，但不自动阻止 Recent Window 按自身批次状态提交；任一已提交批次不得因另一项失败而重复推进。没有重要内容时允许不更新 State。

**本次 Window 中最新的一条真实用户消息不做正文截断**，其完整成本按第 5 节的 U 预留。用户消息正常参与 N/M 计数，不额外建立一条不计数、永久常驻的用户锚点；是否进入窗口仍按范围选取决定。新用户输入作为新事件进入窗口，且只保留一份。末尾注入的 State 不属于这里的“用户消息”。

### 4.3 扩大、缩小与任务恢复

扩大窗口：从当前 Session／分支的原始历史重新选取最近 N 个完整事件，重置选取起点；不能在已截断的文本上继续拼接。缩小窗口同样重新选择合法范围，后续继续执行成批滑动。窗口边界／待处理批次需在现有 Pi 扩展 `custom` 记录或会话元数据中恢复；不得仅依赖进程内存，也不新增独立的 Recent Window 历史日志。相同 `batch_id` 的恢复或重试不得重复提交移动。

`task_resume` 替换当前 State，但保留本次恢复请求、工具调用及返回所在的近期过程；不自动加载旧任务的全部会话。跨任务消息继续显示原所属任务的引用，不重新编号，也不错误归到当前任务。

第一版以本方案创建的、未经过 compaction 的 Session 为主要运行路径。读取旧压缩会话时，应从原始分支恢复对应记录，不把旧 compaction 摘要当作原文或新的 State；不支持的旧表示要明确报告。[S5]

## 5. 唯一预算规则：单条配额

### 5.1 计算公式

先根据本次实际调用模型允许的最大上下文总容量 C_model，计算 Agent 的上限 C，再沿用唯一单条配额公式：

```text
C = floor(C_model * 3 / 5)
Q = floor((C - R - S - O - H - U - X) / M)
```

| 符号 | 含义 |
|---|---|
| C_model | 经核验的实际调用模型最大上下文总容量，单位 token，包含输入与输出 |
| C | Agent 请求总预算上限，固定为 `floor(C_model * 3 / 5)`，不再直接使用模型的完整容量 |
| R | 实际系统提示、记忆规则、工具定义及声明的 MCP 能力 |
| S | 本次实际渲染的完整 State，包括其消息包装 |
| O | 本次配置的最大输出预留，不额外重复计算已包含的推理输出 |
| H | 安全余量、消息协议包装，以及未在其他项计入的完整工具参数／推理字段／签名等 |
| U | 本次 Window 中最新真实用户消息的完整成本；窗口内没有真实用户消息时为 0，不包括已分离为引用的附件原件 |
| X | 本次显式回读、要求完整呈现的内容总成本；没有则为 0 |
| M | 本次 Window 选取的消息总数，不包含 Rule、State |
| Q | 每条普通消息允许展示的文字预算，含引用头及截断标记 |

M 按用户要求使用所有选中消息数，包括已在 U/X 中预留的消息。它比只对待截断消息计数更保守；第一版不做剩余预算二次分配。M 为 0 时直接跳过正文分配，禁止除零。

各成本项互不重复；例如已经计入 U/X 的协议包装不再计入 H。原生工具参数保留在 H，不再从 Q 扣第二次。

**60% 总上限约束整个请求预算。** R、S、O、H、U、X 和普通 Window 文字共同占用 C；最大输出预留 O 已在公式内扣除，不在 C 之外另加，也不再将剩余预算减半。State 和最新用户的“不截断”只是正文策略豁免，不是突破 C 的许可。200 个 Recent Window 事件、500 个 State 事件是事件容量，不能据此保证任何模型都放得下。

例如，经核验模型上限为 1,048,576 tokens（1Mi）时，Agent 上限为 629,145 tokens。[DeepSeek 官方模型列表文档](https://api-docs.deepseek.com/zh-cn/api/list-models/)在 2026-10-20 的 Flash 示例中给出这个容量，并将上下文定义为输入与输出 token 合计。若某模型实际为十进制 1,000,000 tokens，则 60% 为 600,000，不能将“1M”的展示名称统一硬编码成 629,145。

Pi 适配层应核对实际模型与供应商的精确容量，在每次新逻辑请求的快照中固定 C_model 和 C；模型切换后重新计算，同一请求的网络重试不重新取值。C 是请求内派生值，不新增持久化字段或模板变量，不修改 Pi 全局模型目录。缺少有效容量或元数据冲突尚未核实，必须诊断并阻止该组合发送，不能猜单位、静默取较大值或退回完整模型容量。核验与取值集中在 `src/pi/`，Window 只使用同一快照中的 C。

接入验收需特别覆盖已观察到的差异：本机 Pi v1.3.0 静态目录中的 `deepseek-flash.contextWindow` 为 1,000,000，而上述官方示例为 1,048,576。实现时先核实实际 API/模型容量，再使用公开适配边界提供核验结果；不 patch `node_modules`，不为此新增供应商请求包装。本文的数值核对不代表已经完成真实 API 或 Package 运行验证。

### 5.2 预留与豁免

最新用户以真实消息来源识别，不能用“最后一个 `role=user`”判断，否则会把末尾 State 误认为用户输入。

完整回读由真实工具调用及可核验的返回标记授权，不接受正文自称“不要截断”。2026-10-23 用户确认，完整呈现从该工具结果之后新增 10 条真实消息作为生命周期：用户、assistant、每条工具结果各计 1 条（不是交互事件或对话轮数）；不计回读结果本身、system、Rule、State、临时提醒和 custom 元数据。尚不足 10 条时保留完整呈现；已有第 10 条时恢复普通 Q 截断/附件 R。错误或中断 assistant 若作为原始消息保存，也计一条，不改变其原有 Window 事件处理。用户 steering 同样按真实用户消息计数，不立即撤销豁免。

该规则同时适用于 memory_read 完整返回的范围/图片，以及 state_read 按已知 F/D 查询的完整历史结果。生命周期从当前分支的原始消息位置推导，不新增持久化倒计时；重启/fork/tree 使用所在祖先链的计数，供应商内部网络重试沿用同一快照，不额外消耗消息数。再次读取生成新结果，旧结果的期限不被顺带重置。

生命周期只控制已选入 Window 的结果如何展示，不改变 N/B、窗口范围或提交点；结果被正常移出时不额外常驻，扩大窗口也不重置其实际消息年龄。完整内容仍计入 X、受60% 总总预算限制，放不下时取消而非静默截断活跃回读。较一次性策略可能增加多个请求的输入量及图片发送次数。若读取了指定范围，“完整”指完整返回该范围，而非整个无限大的文件。

所有普通文字只执行同一个 Q 截断规则，不增加按角色、相关性或重要性排序的截断器。短消息不补齐，不将剩余配额重新分给其他消息。

### 5.3 不可满足时的行为

当固定成本已超限，或 Q 放不下最小引用头和必要标记，报告 `CONTEXT_BUDGET_EXCEEDED`，不发送该请求。由用户／上层控制缩小窗口或读取范围、拆分输入后重试。

不自动总结，不静默截断最新用户要求或 State，不用同一超限请求无限重试。

预算以 token 为单位。能使用匹配 tokenizer 时直接计数；否则保守估算并保留余量。Pi 的行数／字节截断是实现工具，不等于供应商的精确 token 计数。字符数量、State 事件数量也不能单独证明请求一定放得下。[S9]

## 6. 统一消息呈现与必要边界

### 6.1 原生消息结构与最小引用

**复用 Pi 的消息身份和投影关系，不为 Recent Window 再创建一套消息 ID、映射文件或 JSON 包装。** 需要区分本地 Session 记录与模型 API 消息：

| 层级 | 结构与用途 |
|---|---|
| Session 持久化记录 | `type/id/parentId/timestamp/message` 等字段组织原始历史与分支 |
| Pi 请求消息 | 从记录中取出 `message`，经 `convertToLlm` 和供应商适配器转换；不是把整行 Session JSON 原样发给模型 |
| 原生工具关联 | 保留 `ToolCall.id`、`toolCallId` 等调用与结果关联字段；最终字段名由具体 API 决定 |

Pi 的 `sessionEntryToContextMessages()` 对普通消息取出的是 `entry.message`，不会自动把外层 `entry.id/parentId` 注入给模型；普通用户消息也没有通用的模型可见 Session entry ID。[S5][S7]

因此，本模块不新增引用体系，但仍复用已定稿 Task／State 的 U/A/T 短引用及其解析能力：底层定位到 Pi 的 Session entry／工具调用，模型只看到一个必要短引用，不再重复发送 task、role、entry ID 和映射表。原生工具 ID 负责协议配对，不冒充所有消息共有的来源 ID。

普通文字的最小呈现为：

```text
[T20]
测试结果的可展示正文……
[TRUNCATED]
```

`role`、工具调用结构和结果关联仍由原生消息对象携带，不在正文再复制一份。当前任务只显示 `[U12]`、`[A31]`、`[T20]` 等既有短引用；窗口中保留其他任务的交互时，仅对这类引用补充所属任务以消除歧义。正文中的短引用是既有定位入口的展示，不是新的 Window 编号系统。

引用完整保留；正文按原顺序取可容纳的前部；确有内容省略时才加 `[TRUNCATED]`。不在每条消息后重复解释读取方法，该说明统一放入 Rule。

只裁剪消息对象中的普通内容字段，例如字符串 `content` 或 `content` 数组里的普通文字块 `text`。不截断完整 JSON 序列化串，也不把 Session JSON 当作正文再包一层。原始 Session 不被改写，提供方要求的结构和元信息由 Pi 保留／适配。

普通消息正文中的代码、文件路径、网页链接等使用相同规则。工具若已经截断原件，必须继承其截断状态和完整原件入口，不能伪装成完整结果。

同一消息有多个文字块时，共用一个 Q，而不是每个块各获得 Q。消息原文、时间、身份及既有引用关系不因这次展示长度而改变。

### 6.2 只保留必要的特殊处理

**截断函数接收可展示的文字，不接收整个序列化后的 API 消息对象。** 原生外层结构由 Pi 保留，不靠“符号应该排在前面”维持正确性。

| 内容 | 本版处理 |
|---|---|
| 普通 user／assistant／tool 文字 | 同一个 Q；仅最新用户及本次完整回读豁免 |
| 原生 `tool_call_id`、工具名、`arguments`、调用结果配对 | 不改写、不剪成半段 JSON；按实际占用计入 H |
| 供应商要求回传的推理字段／签名及其受保护内容 | 保持原样，计入固定开销，不作为普通正文截断 |
| 图片／文件二进制块 | 默认整体替换为原件引用，不截断 base64；明确读取且模型支持时才完整发送并计入 X |

Pi 原生工具调用的 `arguments` 是独立 JSON 对象，图像也是独立内容块，不能等同于一串正文中的符号。[S7]

除此之外，不新建工具调用文本化系统、不重写历史参数、不增加语义截断模型。若不可裁剪字段本身过大，就按预算不可满足处理，而不是破坏协议。

## 7. 原生读取和大输出：只做薄适配

复用 Pi `read` 的 `offset/limit`、截断函数的行数／字节边界与标记，以及 Bash 输出的 `fullOutputPath`。[S8][S9][S10]

适配流程：

```text
Pi 返回结果或原件路径
    → 必要时把临时原件转存至 blobs，并按内容哈希去重
    → 绑定 Task 内的 T／R 引用
    → 进入统一的引用头＋正文＋截断标记呈现流程
```

Bash 的完整输出目前可能位于系统临时目录，因此跨会话证据需要持久保留；不重写原生输出收集器。[S11]

2026-10-21 用户批准阶段 4：R 与必要完整原件的定位分别使用 Task §9 的 memweave.aliases.v1 / memweave.originals.v1；正文字符、完整性和图片回读遵循 State §16。原始 Session 已有图片按内容块定位，不重复复制；仅原生工具元数据提供的完整临时输出按哈希转存。完整 Q/X 预算仍在阶段 5 接通。

普通小消息直接引用 Session。图片和二进制文件默认只展示引用。只收到截断结果、没有原件时，明确记录不完整，不能承诺之后一定能读回全文。

`memory_read` 使用 Symbolic State 文档定义的统一读取协议，支持批量引用、字符偏移和返回长度限制。完整回读结果在本次请求计入 X；普通搜索和不要求完整呈现的结果仍按普通消息处理。本模块不增加窗口专用读取、搜索或子 Agent。

## 8. State 末尾注入

本版将 `context_compose()` 改名为 **`state_insert()`**，职责严格限定为：在已完成选取和展示的 Window 末尾，插入一次当前 State。

State：

- 按已定稿机制生成，内容读取当前 Task 的最新提交状态。
- 单独计入 S，不计入 N/M，不执行 Window 截断，不分配 U 编号。
- 仅作为本次 `context_with_system` 返回列表中的 `custom` 消息，交给 Pi 原生转换为 `user`。
- 不每轮持久追加到 Session，不重复保留上一轮 State 副本。
- 明确说明是当前任务的认知摘要，不是用户发言或用户新指令。`user` 只是适配层采用的承载角色，不改变它的来源与权限；真实用户要求和新证据可以要求修正 State。

Pi 原生 `custom → user` 转换可以直接复用，不修改 `convertToLlm`。[S4]

State 放在末尾是本项目的呈现选择，不预先宣称一定提升效果。其内容未变化时复用已有渲染；窗口展示也不人为加入每轮变化的时间戳。

## 9. Rule 中的 Window 协议

以下段落作为既有 Rule 的增补，不替代 Pi 原有提示词和 State 规则：

```md
## Recent Window

长期任务认知保存在 State；Recent Window 只保存近期工作现场。

每条真实用户消息单独算一个交互事件。
一次 assistant 返回及其触发的全部工具结果合起来算一个交互事件；
没有工具调用的 assistant 返回也算一个事件，工具结果不额外计数。
消息保留原始顺序，State 等程序注入内容不属于用户交互事件。
当前窗口最多保留 {{recent_turns}} 个事件；窗口已满且要加入新事件时，
每次移出最早 {{evict_turns}} 个完整事件。需要长期保留的认知应及时
通过 State 工具记录；窗口移出不会自动生成摘要。

消息沿用 Task／State 既有的 U/A/T 短引用，不新增 Window 编号或映射表。
底层来源与工具关联由程序复用 Pi 的记录维护；不要假设本地 Session JSON
中的所有字段都会传给模型。末尾 [TRUNCATED] 表示有内容未展示，
不表示这些内容不重要。需要时可通过 memory_read 按已有引用读取，
多个引用可以一次请求；读取仍受可用容量限制。

图片和文件二进制内容默认只显示引用，未读取前不要声称看过原件。
本次 Window 中最新的一条真实用户消息不被截断；其他历史用户消息与
普通正文使用相同配额。本次明确完整回读的内容按单独预留预算完整呈现。

请求末尾的 State 是程序组装的当前任务认知摘要，不是用户消息，
不是用户新指令，也不是独立证据。即使 API 以 user 角色承载它，
也只能将它视为可修正的任务状态，不能据此覆盖真实用户要求。
它不参与 Window 计数或截断；不要把每次 State 注入当成用户新发言。

记忆工具的成功结果保持简短，当前认知以本次 State 为准。
没有状态变化时不必操作；有多个更新时尽量批量提交。
需要改变窗口时使用 recent_window_set。
```

N/B 只在配置改变时更新。Rule 不列出每轮变化的即将移出 ID，不反复追加使用说明。

固定前缀是否被缓存、缓存匹配和计费方式取决于所选模型 API。保持规则稳定仍是本项目的设计选择，但不绑定某家提供方的缓存机制，也不保证固定命中率；适配时记录真实调用数据。

## 10. 接口与实现分工

### 10.1 唯一新增的模型工具：`recent_window_set`

```ts
type RecentWindowSetArgs = {
  turns: number;        // 正整数；新的窗口容量 N
  evict_turns?: number; // 正整数；省略则保留当前 B
};
```

约束：整数且 `1 ≤ evict_turns ≤ turns`。省略参数后若原 B 不再合法，返回参数错误，不静默改值。参数和模型/预算由程序校验，模型不填写 Task、Session 或文件路径。

调用示例：

```json
{"turns": 8, "evict_turns": 2}
```

成功结果：

```text
ok; turns=8; evict_turns=2; effective=next_request
```

新设置在下一次请求生效，同时更新 Rule 中的 N/B 并从原始历史重选范围。工具调用及结果正常留在 Window；不因此自动设置 `terminate`，因为下一轮通常还要使用新窗口继续任务。

### 10.2 四个内部函数

下面是项目函数，不是四个新服务或四次模型调用。

| 函数 | 主要输入 | 输出与职责 |
|---|---|---|
| `window_select()` | 原始会话视图、当前分支边界、N/B | 选中消息、最新用户标记、完整回读标记及 M；不截断正文 |
| `window_allocate()` | 当前模型容量、有效 Rule/工具、State、选中消息 | 唯一的 Q 与固定预留；不可满足则返回错误，不二次分配 |
| `window_render()` | 选中消息、Q、既有原件引用 | 复用原生消息结构，仅裁剪普通内容字段；最小短引用与 tag，不新增编号映射 |
| `state_insert()` | 已渲染 Window、当前 State、可选 State／Recent Window 待处理批次 | 追加当前 State；State 提醒附在 State 消息末尾，Recent Window 提醒作为其后的临时消息追加；不保存新历史 |

大输出转存属于现有工具适配，State 渲染属于 State 模块，不再塞入上述四个函数的职责。

### 10.3 Pi 接入示意

本节与 Rule 技术稿共用一个 `context_with_system` 处理器，不另注册一个普通 `context` 窗口处理器。完整接线示意见 Rule §6.1，顺序固定为：

```text
检查宿主/有效设置 → 捕获 Task/配置/State 快照 → 读取并渲染 Rule
  → 获取有效 system 与工具声明（R）
  → 对非 system 消息执行 window_select
  → window_allocate（唯一的 Q）→ window_render → state_insert
  → 返回 [有效 system, Window, 必要的 Window 提醒, State（含管理提醒）与预算快照]
失败：先 ctx.abort()，再报告，丢弃本次局部结果
```

上述名称是项目内部函数，不是新增的 Pi API、服务或持久化字段。`event.messages` 是本次请求输入，不能仅用磁盘旧内容替换而遗漏刚进入执行流程的新消息。扩大范围时从原始分支补齐缺失内容，按来源 ID 去重。

Pi 的上下文 runner 会捕获处理器异常，`throw`、返回 `[]` 或“组装失败”标记本身都不保证停止发送。本扩展使用公开 `ctx.abort()`；每个宣称支持的宿主/提供方组合须观察模型/HTTP 边界，证明错误请求未发出。不包装底层 stream，不为此增加第二次计数或截断。[S3][S13]

一次请求的快照固定；底层网络重试不重新读取 Rule、消耗完整回读豁免或推进批次。新逻辑请求重新准备，Window/State 的提交点仍按原契约，不因改换 hook 提前提交。后置扩展追加未预算内容、覆盖 system 或再次插入 State 时不能宣称兼容，须按组合验收并报告边界。

## 13. 本版边界与定稿状态

本版只做 **选取 → 分配 → 展示 → State 注入**。不做摘要 Agent、语义路由、历史工具调用文本化、独立 Window 存储或操作日志上下文。

正文统一截断，只有真实输入、显式完整回读、State 及协议要求内容适用已列明的处理。不能把“引用放在前面”视为损坏外层协议也无妨的保证。

**本文件为 Recent Window 与上下文组装 v1.0 正式定稿。** 2026-10-20 增量同步原生 Package 接入、60% 总预算和默认参数；其余机制沿用已确认方案。

## 13. 阶段 5 恢复协议（2026-10-22 用户确认）

Window 定位仅写入 Pi custom `memweave.window.v1`，不另建 Window 历史文件。每条为轻量快照：`{stage, recent_turns, evict_turns, boundary_entry_id, pending, request_anchor_entry_id, completed_by}`。stage 为 prepare / commit / reset；boundary_entry_id 是最后已移出事件的原生起始 entry ID，尚未移出为 null；pending 是按事件顺序排列的 `{batch_id, candidate_event_ids}` 数组，每批恰好 B 个完整事件。用户事件以 user entry 定位，assistant 事件以 assistant entry 定位，工具结果随事件整体移动。不存正文或另造消息编号。

batch_id 由来源 Session、前边界和候选身份稳定生成。request_anchor_entry_id 是本次请求准备前最后一条原生消息；commit 的 completed_by 为完成提醒处理的原生 assistant entry ID，其余阶段为 null。prepare 可靠追加后才能发送提醒；对应 assistant 成功完成且工具结果齐备后，按 pending 顺序逐批追加 commit，每条前移一个批次并保存剩余 pending。每条 commit 可靠落盘是该批唯一提交点；部分失败只保留未提交批次，不重复移动已提交批次。模型错误、中断及未齐备工具结果不得提交；工具业务失败已有完整结果时，不妨碍 Window 按自身规则提交，也不表示 State 写入成功。

正常超限通常只有一批。禁用扩展后继续交互、或待处理批次期间不断中断且加入新事件，可能形成多批积压；同一请求临时保留所有待移出候选，末尾合并为一次短提醒，该轮结束后顺序提交至本次快照满足 N，不为每批额外调用模型。过程中新增事件继续按既定单位计数，由下一请求判断是否再次超限。普通重启不凭空产生批次，重组同一历史不推进边界。

按当前分支祖先链读取最新合法快照，校验事件身份、连续性、顺序和工具配对；fork 继承分叉点之前的状态，后续独立推进，tree 回退采用对应祖先状态。首次接入无 Window 元数据时从原始分支建立事件索引，超限按 B 分批提醒；不得用旧摘要冒充原文。无法解释的原生／第三方表示应诊断，不静默丢弃。未绑定 Task 不伪造短引用；附件尚无可用 Task 来源时明确说明须先建立 Task 绑定，不声称可回读。

`recent_window_set` 沿用 `memweave.scope.v1` 覆盖 N/B，下一请求检测参数变化并追加 reset，从原始历史重选最近 N 个完整事件，取消旧 pending；已提交 State 不回退。同一原生调用重试不重放已完成设置；同轮冲突的多次窗口设置，或与 Task 切换混合导致 scope 归属不明确时拒绝，允许与普通 State 维护并行。全局默认值与其他进程不改写。

完整回读 X 依据原生 memory_read 或 state_read 历史查询调用、实际工具结果及机器标记核验，按 §5.2 的后续 10 条真实消息期限判定；可同时有多个活跃结果，网络重试复用同一快照。未知图片 token 费用不能以固定平均值冒充精确值；无匹配 tokenizer 时使用保守估算和安全余量，不能建立保守费用边界时取消该组合。输出默认按 Agent 预算 10% 与宿主/提供方上限的较小值，并通过公开出站 hook 与实际参数对齐；显式输出设置按实际预留，异常组合取消。

## 14. 比例规划与请求快照（2026-10-23 用户确认）

本节取代旧默认窗口/预算中的固定值，完整增量决策见 ../CONTEXT_BUDGET_DESIGN.md。C=floor(C_model*3/5)，八项规划比例为 State 12.5%、普通 Window 37.5%、输出 10%、系统/Rule/AGENTS/工具 15%、最新用户 5%、完整回读 10%、原生历史协议 5%、安全 5%。整数向下取整，余数归 Window。四个 State 默认值为 500/100/100/20。N/B 省略时自动、已有显式数值/分支覆盖优先，计算见 Rule §3。

R、S、U、X、P 按实际核算且不重复扣除，其他分区未用额度给 Window；必要系统/用户/完整回读超规划也可挤占 Window。安全 A=floor(0.05*C) 不借出。默认输出 O=min(floor(0.1*C),提供方/宿主输出上限)，显式用户输出按实际预留并校验。唯一公式为 Q=floor((C-R-S-O-P-A-U-X)/M)，M 仍含 U/X。旧公式 H=P+A。参数、需回传的 reasoning/signature、角色包装及临时提示计 P，不计本地 timestamp/usage/details/Session 外壳。普通正文、引用头及截断标记共享 Q；不裁剪参数或 opaque 字段。

DeepSeek Flash 使用固定来源/校验和的官方 V4.1 tokenizer 数据和纯 JS 运行依赖；协议模板使用保守开销和 5% 安全余量，并通过真实 usage 校验，不宣称整个供应商模板逐 token 精确。其他未匹配组合明确标记保守估算。Unicode 截断后重新计数，普通字面量控制 token 拼写不当成特殊 token。

同一 context_with_system 快照完成 Rule/Window/State；末尾同一临时 State 消息附预算（无 Task 也显示快照），Window 提醒放它之前。快照自身预留并计 P，生成后复核。显示各项规划/实际、State 条数/上限/管理线、N/B、M/Q 和实际输出上限。它不是用户要求或证据，不持久化、不计真实消息。

唯一额外出站接线为公开 before_provider_request，将实际输出字段与已预留 O 对齐并检查模型；不改消息、不重新预算、不包装 Loop。无法核实 payload、模型变化或预算失败先 ctx.abort 再报告。State token 管理/准入见 State §18，不改变 Window 批次和回读生命周期。

## 15. 有界来源定位缓存（2026-10-24 用户确认）

来源核验使用当前请求的原始快照直接比较内容，不对整条消息反复 JSON.stringify。role/timestamp/toolCallId 等短字段仅定位候选；缓存命中也须确认 Pi entry ID 与完整内容，不保存“通过”结论。未命中集中扫描一次原始来源；仍无法匹配时才按需调用一次 Pi 原生 buildSessionProjection，保留 context_edit/旧 compaction 的现有兼容与取消边界，不复制投影算法。

每个实例最多缓存 8192 个定位项和约 16 MiB 数据预算，LRU 淘汰；只存有长度上限的键、entry ID、数组位置和估算开销，不存正文/图片/投影或磁盘副本。Session/分支切换和 reload 清空，正常追加可复用；当前条目被修改时仍须被比较发现。请求临时索引和投影仅在请求内存活。具体上限核算、失效与测试边界见 ../SOURCE_VERIFICATION.md。本优化不改变 Window/State/回读/预算、模型工具、持久化格式或原始历史，不承诺消除 Pi 本身构造/复制完整上下文的工作。
