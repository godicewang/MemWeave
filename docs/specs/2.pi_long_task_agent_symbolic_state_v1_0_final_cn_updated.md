# Pi Long Task Agent — Symbolic State 技术方案 v1.0

本方案已按当前讨论定稿：Task 级 Symbolic State；`state.json` 为追加式事件记录，`state.md` 为程序每轮组装的当前认知；默认 500 事件窗口，每批管理 100，Agent 最多保留 20；核心类型仅 Goal / Fact / Decision；State 接口为 `state_append`、`update_goal`、`modify_fact`、`state_read`、`state_remain`，另提供统一原文读取工具 `memory_read`；事实修改必须原子地 archive + append；State 操作结果极简并进入 Recent Window；不设独立 Memory Operation Log。

## 1. 定位

State 是 Task 在长期执行过程中最重要的认知演化记录：当前 Goal、重要 Fact、关键 Decision，以及重要转折和结果。Session 保存完整经历；State 保存经历沉淀出的长期认知。

## 2. 文件结构

```text
~/.pi/memory/
├── index.json
└── <cwd_key>/
    └── tasks/<task_id>/
        ├── state.json
        └── state.md
```

`index.json`：跨工作区 Task 索引，强制保存 `task_id`、项目名、摘要、关键词、workspace 等。

`<cwd_key>`：直接复用 Pi 的 workspace/cwd identity 口径。

`state.json`：唯一持久化事实源，追加记录 State 操作及演化过程，不保存快照。

`state.md`：当前 State 的运行时呈现。每次 LLM 调用前由程序根据 `state.json` 重建，不由模型直接编辑。

## 3. State 数据模型

仅保留：

- Goal：当前 Task 目标；允许谨慎调整。
- Fact：已经确认的重要事实；必须有 evidence。
- Decision：重要判断、选择、结论；必须有 evidence。

不引入 Plan、Hypothesis、知识图谱、Embedding State 等。

如果用户提出的新目标仍依赖当前 Task 的主要上下文，可以 `update_goal`；如果已经成为独立任务，应结束当前 Task 并创建新 Task。

## 4. ID 与证据

State ID 按 Task 作用域编号：`F1/F2...`、`D1/D2...`。U/A/T 等引用同样以 Task 为作用域。

Fact / Decision 必须提供证据引用，例如 `U3`、`T5`、`F1`。引用指向原始消息、工具结果或已有 State 事件，程序负责校验其是否存在。

## 5. state.json

采用追加式 JSONL/事件记录。例如：

```json
{
  "op_id": "task_001_001",
  "op": "append_fact",
  "time": "2026-10-16T10:00:00+08:00",
  "id": "F1",
  "fact": "xx程序存在加载300ms延迟过长问题",
  "evidence": {
    "U3": "用户提到存在延迟问题",
    "T2": "建立脚本测试延迟",
    "T5": "执行脚本确认延迟"
  }
}
```

Decision：

```json
{
  "op_id": "task_001_002",
  "op": "append_decision",
  "time": "2026-10-16T10:05:00+08:00",
  "id": "D1",
  "decision": "优先检查xx模块，而不是修改整体架构",
  "evidence": {
    "F1": "已确认主要问题是加载延迟",
    "T5": "日志显示主要耗时集中在xx模块"
  }
}
```

Goal：

```json
{
  "op_id": "task_001_003",
  "op": "update_goal",
  "time": "2026-10-16T10:10:00+08:00",
  "goal": "重点解决xx模块加载性能问题",
  "evidence": {"U8": "用户明确缩小任务目标"}
}
```

## 6. 事实修改

禁止直接修改或删除旧 Fact。事实变化必须通过 `modify_fact` 原子完成：

```text
archive 旧 Fact
+
append 新 Fact
```

例如：

```json
{
  "op_id": "task_001_010",
  "op": "modify_fact",
  "time": "2026-10-16T11:00:00+08:00",
  "archive": ["F1", "F2", "D1"],
  "append_fact": {
    "content": "通过修改xx模块，加载延迟从300ms降低至20ms",
    "evidence": {
      "F1": "原始问题",
      "F2": "问题定位",
      "D1": "处理决策",
      "T20": "修改后测试结果"
    }
  }
}
```

约束：`archive` 非空；必须存在 `append_fact`；新 Fact 必须有 evidence。`archive` 不能作为普通清理手段。

## 7. 固定 State 窗口

默认参数：

```text
MAX_EVENTS      = 500
EVENT_MAX_CHARS = 100
EVICT_BATCH     = 100
KEEP_LIMIT      = 20
```

活动 F/D 达到 500 或完整 State token 达到规划预算 80% 时，程序准备管理最早 100 个候选。程序不在 Rule 中动态列出候选，也不枚举全部 100 个 ID；而是在本次请求末尾的 State 消息中附加一次临时提醒，以一个明确边界表示待移出范围，例如“F801 之前的 State 事件将被移出”。Agent 可通过 `state_remain` 选择边界之前需要保留的事件；程序负责校验并执行窗口移动，Agent 负责重要性判断。

以上默认值与 Rule 技术稿 §3 对应。2026-10-23 用户确认将默认容量调整为 500、候选批次 100；正文上限 100 字符、最多保留 20 及 1/10 比例不变。100 表示候选数，扣除获准保留项，不要求净移出 100。Agent 总上限为模型容量 60%，State 规划/准入预算为 Agent 的 12.5%，不静默截断正文；详细规则见 §18 和 Recent Window §5。

提醒不写入 `state.json`，不作为新的 State 事件，不参与 State 窗口计数。窗口滑动本身则由程序作为独立的 State 操作记录追加到 `state.json`，至少记录批次标识、移出范围、保留列表、时间及提交结果；重建 `state.md` 时依据这些记录恢复活动窗口。操作记录可采用如下形式：

```json
{
  "op_id": "task_001_op_014",
  "op": "slide_window",
  "time": "2026-10-19T10:30:00+08:00",
  "batch_id": "state_batch_003",
  "evicted_range": {"from": 701, "to": 900},
  "retained_ids": ["F17", "D23"],
  "status": "committed"
}
```

其中序号和 ID 仅为示例；实际记录必须引用程序确定的事件范围与本批次有效保留结果。原始事件始终保留在 `state.json`，退出活动窗口不等于删除原始记录。窗口移动的提交点是：程序已将包含 `batch_id`、移出范围、保留列表、时间和提交状态的 `slide_window` 操作可靠追加到 `state.json`，并能据此重建活动窗口。`batch_id` 用于幂等识别；同一批次重试不得重复追加或再次推进窗口。只有本批次成功提交后，下一次组装才移除提醒；若校验或持久化失败，活动窗口不变，待处理批次和提醒必须保留，不能先清除再重试。

因此：

```text
程序控制容量
+
Agent 控制重要性
```

而不是让 Agent 自己无限管理 State。

## 8. state.md

每次模型调用前程序由 `state.json` 重建：

```md
# Symbolic State

task_id: task_001
state_version: 13

## Goal

优化支付系统中 xx 模块的性能问题

## Facts

F1 xx程序存在加载300ms延迟过长问题
e: [U3, T2, T5]

F2 xx模块加载延迟10ms，不存在明显性能瓶颈
e: [T6, T7]

## Decisions

D1 优先检查xx代码
e: [F1, T5]

D2 修改xx模块并重新测试
e: [F2, T8]
```

State 压缩后，旧事件从当前 `state.md` 消失，但仍保存在 `state.json`，因此可以重新追溯和审计。

## 9. 接口

### `state_append`

批量新增 Fact / Decision。

```json
{
  "items": [
    {"type": "fact", "content": "...", "evidence": {"U3": "..."}},
    {"type": "decision", "content": "...", "evidence": {"F1": "..."}}
  ]
}
```

程序生成 ID、`op_id`、时间，校验证据，写入 `state.json` 并更新当前 State。

#### 调用示例

假设 `F1` 已经存在，且 `T8` 已返回性能分析结果。Agent 在一次调用中记录新事实和处理决定：

```json
{
  "items": [
    {
      "type": "fact",
      "content": "xx模块加载耗时占本次总耗时的90%",
      "evidence": {"T8": "性能分析确认该模块的耗时占比"}
    },
    {
      "type": "decision",
      "content": "优先检查xx模块的加载流程",
      "evidence": {
        "F1": "既有的加载延迟问题",
        "T8": "本次分析显示主要耗时集中在xx模块"
      }
    }
  ]
}
```

程序按顺序校验证据并生成事件 ID，一次提交这批新增内容；调用结果只返回简短的成功信息。示例中的 `F1` 是调用前已经存在的事实，不要求模型猜测本批新生成的编号。

### `update_goal`

```json
{
  "goal": "重点解决xx模块加载性能问题",
  "summary": "聚焦支付模块加载性能并验证优化结果",
  "keywords": ["支付模块", "加载性能", "优化验证"],
  "evidence": {"U8": "用户明确调整目标"}
}
```

`summary` 与 `keywords` 由 Agent 根据新 Goal 同步更新，用于刷新全局 `index.json` 中的任务发现信息；若项目归属确实变化，再提供更新后的 `project_name`。这些字段属于 Task 索引元数据，不是新增的 State 类型。

是否调用由 Agent 决定；谨慎使用。

### `modify_fact`

```json
{
  "archive": ["F1", "F2"],
  "append_fact": {
    "content": "xx模块已完成优化，加载延迟从300ms降低至20ms",
    "evidence": {"F1": "原始问题", "T20": "修改后测试"}
  }
}
```

由程序原子执行归档与新增。

### `state_read`

```json
{"task_id": "task_001"}
```

主要用于 Agent 主动查看其他或历史 Task 的 State；当前 Task 正常运行时不需要，因为当前 `state.md` 已自动加载。它只读取 State，不切换当前 Task，也不返回原始会话全文。

2026-10-23 用户确认增加受控的历史 F/D 查询：可选 `event_ids` 与 `max_total_chars`，不传 ID 保持以上当前 State 读取行为；指定 ID 时读取已归档或已移出的原认知及证据，详见 §17。

### `memory_read`

用于根据已有引用读取原始消息、工具结果或已保存的大文件／日志。Pi 提供底层 Session 与文件读取能力，但没有一个可直接供模型按本项目 U/A/T/R 引用读取、支持多引用和统一返回预算的现成工具，因此新增一个薄封装；它不搜索未知引用、不切换 Task、不修改 State，也不调用子 Agent。

输入：

```json
{
  "items": [
    {"ref": "T20", "offset": 0, "limit": 2000},
    {"ref": "R3", "offset": 200, "limit": 1000}
  ],
  "max_total_chars": 5000
}
```

- `items`：必填数组，允许一次读取多个已知引用。每项的 `ref` 为当前 Task 的 `U/A/T` 引用，或程序此前分配的跨 Task／外部原文别名 `R`。
- `task_id`：每项可选，指定其他 Task 时读取该来源已知 U/A/T，并返回当前 Task 的 R 别名；省略时沿用当前 Task。不得用它跨 Task 解释 R。
- `offset`：可选，非负整数，表示从规范化后的文本内容起始处跳过的字符数，默认 `0`。
- `limit`：可选，正整数，表示该引用本次最多返回的字符数；省略时由 `max_total_chars` 统一限制。
- `max_total_chars`：可选正整数，限制本次所有条目合计返回的正文字符数；由程序设置安全默认值和上限。超出预算时按请求顺序返回可容纳内容，并标记未完整返回。

返回每项的 `ref`、来源 Task（如适用）、`content`、实际 `offset`、原文总字符数（可取得时）及 `truncated`／读取状态。引用不存在、原件缺失或内容不完整时必须明确报告，不得伪装成完整原文。`offset`/`limit` 针对统一后的文本字符位置；底层文件读取可以适配 Pi 的行范围读取，但返回语义保持一致。

程序负责把引用映射到 Pi Session entry 或 `blobs/` 原件，并复用 Pi 的 SessionManager、文件范围读取和大输出保存机制。`R` 只是当前 Task 使用的定位别名，不改变来源 Task 的编号，也不自动恢复来源 Task。此工具只读取已知引用；模糊查找 Task 仍由 `task_find` 负责。

### `state_remain`

用于 State 窗口移动前，声明需要继续保留的事件列表。

```json
{
  "event_ids": ["F17", "D23", "F31"]
}
```

`event_ids` 为字符串数组，只能包含程序本次提示所标定的待移出范围内、当前 State 中确实存在的事件 ID；可以传空数组，表示本次不额外保留。提醒只提供边界，不要求把整批候选 ID 全部复制到提示中。

保留列表长度不得超过 State 窗口长度的 `1/10`，同时遵守第 7 节既定的 `KEEP_LIMIT`。按当前默认配置，比例上限为 200，但 `KEEP_LIMIT = 20`，所以实际最多保留 20 个。程序校验范围和数量，记录窗口滑动轨迹，并执行窗口移动；该接口不修改原文、不删除持久化事件。Agent 可以提交空列表；只有仍有长期价值的事件才需要主动保留。若 State 窗口提醒与 Recent Window 提醒同时出现，Agent 可以在同一轮 assistant 响应中分别调用 `state_remain` 与 `state_append`；两项操作独立校验、独立提交，不要求串行等待另一项完成。Recent Window 的 `state_append` 仅在确有长期价值认知时调用。

## 10. Tool Result 与上下文成本

State Tool Result 保持极简，例如：

```text
State updated: v13
```

不返回完整 State。Tool Call / Tool Result 正常进入 Recent Window；因为结果很短，额外成本有限。Rule 明确告知 Agent：State 会在下一轮自动重新组装，无需依赖历史 Tool Result 作为当前 State。

State 操作不再设置独立的第四部分 Memory Operation Log；其调用本身已经存在 Recent Window，且 `state.json` 保存完整操作记录。

## 11. Pi 能力复用

复用 Pi 的 Session 消息记录、Tool Call/Tool Result、Context 构建入口、`context_edit`、workspace/cwd identity 和 Extension Tool 注册机制。

新增的核心能力仅包括 Memory 目录、State Event Log、State Reducer、窗口控制、证据校验、五个 State Tool，以及一个薄封装的 `memory_read` 原文读取 Tool。

## 12. 完整演化示例

初始：

```text
F1 发现启动延迟300ms
D1 优先检查xx模块
F2 定位到xx模块
D2 修改xx模块
F3 修改后降低至20ms
```

任务完成后：

```text
modify_fact(
  archive=[F1,F2,D1,D2,F3],
  append_fact="xx模块已完成优化，启动延迟从300ms降低至20ms"
)
```

当前 `state.md`：

```text
Goal: 解决xx模块启动性能问题

F4 xx模块已完成优化，启动延迟从300ms降低至20ms
   e: [F1,F2,D1,D2,F3,T20]
```

而 `state.json` 仍完整保存整个演化过程。

## 13. 核心原则

```text
Session
= 完整经历

state.json
= State 演化记录

state.md
= 当前认知

Agent
= 判断什么重要

程序
= 控制容量、格式、持久化和组装
```

最终目标不是保存更多历史，而是在固定成本下持续保存一个 Task 最重要的长期认知。


## 14. 阶段 2 提交约定（2026-10-21 用户确认）

初始 Goal 使用既有 update_goal 记录，初始 state_version=1；版本等于已提交 State 操作记录数，批量新增的每条 Fact/Decision 各计一条。state_append 必须为非空批量，正文按 Unicode 码点校验配置上限，不静默截断。整批 evidence 只能引用提交前已存在的来源；不能猜测本批新编号。

沿用 op_id，以 Task、Pi Session、来源 assistant entry ID、原生 tool call ID 及条目序号确定稳定标识。同一原生调用重试不重复提交；不同轮即使复用 tool call ID 也不是同一事务。

Task 写锁内完整校验后，原子替换“原 JSONL 字节＋本批记录”；旧前缀不变，不新增快照或事务日志。state.json 是唯一认知提交点，state.md 和索引版本可重建；派生写入失败须报告已提交版本、Task ID 和失败阶段。Task State 在所有绑定它的 Pi Session/分支间共享，不随 tree 回退撤销。

U/A/T 的存在性由 Task 规范 §8 的 Pi custom 引用及原始条目核验；仅已完成工具结果可作 T 证据。阶段 2 不提前实现 R 别名分配或 memory_read，也不猜测未来引用。


## 15. 阶段 3 窗口与恢复约定（2026-10-21 用户确认）

### 计数、满窗与保留

500 个事件的计数单位为当前活动 Fact/Decision；当前 Goal 独立、常驻呈现，不占 F/D 名额。Goal 更新、modify_fact 和 slide_window 等操作仍按 §14 递增 state_version，版本不等于活动条目数。F/D 编号按完整历史继续，不因归档或移出而复用。

当前活动 F/D 达到 state_max_events，或达到 State token 规划预算 80% 时准备最早 min(state_evict_batch, 活动数) 个候选。提醒的同时正常载入新认知，在 token 准入允许时允许 State 暂时超过 500，不排队、不静默截断、不自动移除候选；只有 state_remain 成功提交后才移除未保留项。如果仍达到容量，下一请求准备新批次。实际保留上限按本次请求活动数的 1/10、配置上限与候选数取最小值，固定在请求批次元数据中。

保留项维持原始操作顺序，不移动到队尾、不重编号；后续满窗时可能再次成为最早候选。临时超容量不豁免最终 token 预算；预算无法满足时取消请求，不能截断 State。

### 归档、范围与证据

modify_fact 的 archive 必须包含不重复、确实已记录且尚未被归档的 F/D ID；允许归档已经退出活动窗口的历史条目，拒绝未知 ID 和已归档 ID。归档与新增 Fact 在同一个既有 modify_fact 记录中原子提交。新 F 编号由重放完整历史的计数唯一生成，不新增持久化 ID 字段。历史 F/D 仍可作为证据，归档或退出窗口不抹除原始依据。

slide_window 沿用 §7 的结构；evicted_range.from/to 为本批候选首尾对应的原始 State 操作记录 1-based 序号。范围内已归档或已移出的历史不重新激活；retained_ids 必须属于本批当前候选。原始 JSONL 保留所有记录。

### 请求批次恢复

需要窗口管理时，使用 Pi custom 类型 memweave.state.request.v1 保存 {task_id, batch_id, evicted_range, candidate_ids, keep_limit, state_max_events, state_evict_batch}。不保存提醒正文、State 正文或证据正文，不新增记忆文件；工具从来源 assistant 的祖先链定位当时的记录，模型参数仍只有 event_ids。

## 16. 阶段 4 回读协议（2026-10-21 用户确认）

沿用 §9 参数并增加 items[].task_id。items 非空；offset/limit 为安全整数，offset 非负、limit 正数。max_total_chars 默认 8000、最大 50000，按请求顺序分配正文字符预算；单项失败不遮蔽其他结果。无剩余预算的条目明确报告，不伪称完整。

统一正文按 Unicode 码点计算 offset/limit/total_chars。仅原条目 text 块按原顺序以一个换行拼接，CRLF/CR 统一为 LF，不去空格、不做 Unicode 归一化。读取原 Session 条目，不读取 context_edit 或请求截断后的投影。assistant 工具名/原生调用 ID 作为来源信息返回，arguments、thinking/signature 保留在 Pi Session，不拼入正文；未知块明确报告。完整性针对这一可读正文，不声称重建整个供应商协议消息。

逐项返回 ref（输入引用）、resolved_ref（当前 Task 可复用引用）、source_task_id、source_ref、content、offset、total_chars（原件完整可得时）、truncated、source_complete、range_complete 和 status，并保留来源 Session/entry/tool call 定位。truncated 说明正文未全部返回，source_complete 说明原件是否完整，range_complete 说明请求范围是否完整返回；三者不能混用。失败说明不充当原文。

原生 Bash 的 details.fullOutputPath 在结果进入 Session 后、下一请求前转存到既定 blobs，turn_end/恢复补验；只认可实际工具元数据，不扫描正文路径。仅截断片段可得时 source_complete=false，total_chars 不冒充全文长度。不能读取业务文件当前内容冒充历史工具的原件。blob 读取核验哈希与字节长度，保存失败明确诊断，不回退为完整。持久化类型及编号见 Task §9。

## 17. 历史 State 查询（2026-10-23 用户确认）

### 目的、范围与影响

当前认知可以引用已退出活动窗口的 F/D，因此必须能按已知 ID 追回它们的原正文与证据解释。复用 `state_read`，不扩大 `memory_read` 的 U/A/T/R 范围；不搜索未知认知、不递归展开全部证据、不切换 Task、不分配 R，也不改变 State 或原始 Session。查询结果增加上下文占用，但受条目数、字符预算及最终请求预算约束。

### 接口与技术细节

旧调用 `{task_id}` 原样返回当前 State Markdown。新调用为：

```json
{"task_id":"task_001","event_ids":["F1","D2"],"max_total_chars":8000}
```

`event_ids` 为 1–50 个已有格式的 F/D ID，按输入顺序逐项读取（重复 ID 亦按输入顺序处理）。`max_total_chars` 仅用于历史查询，默认 8000、最大 50000，为正安全整数；不带 `event_ids` 时不得单独填写此参数。未知 Task/损坏 State 是请求错误；未知条目逐项返回 `not_found`，不遮蔽其他结果。

历史查询返回 `{task_id,state_version,items,total_chars}`。每项包含 `id,status,content,evidence,total_chars,returned_chars,truncated`；已存在项另含 `kind,archived,in_window`，分别表示类型、是否已归档、当前是否活动。已归档或移出项仍从唯一 `state.json` 重放所得的完整历史读取，保留原文、证据和 ID，不从当前 state.md 猜回。不存在项不伪造正文或状态。

字符预算按 Unicode 码点依输入顺序分配，计入正文与实际返回的 evidence 引用键/解释文字；不计 JSON 包装和固定状态字段，这些仍受最终请求总预算约束。每项先取正文前缀，再按原顺序取证据解释；证据引用键不可截断。`total_chars`（单项）是完整正文及证据的字符数，`returned_chars` 为实际返回数，`truncated` 明确说明是否完整。无剩余预算时返回 `budget_exhausted`；有部分预算但未完整时返回 `ok` 且 `truncated=true`。顶层 `total_chars` 为实际返回的正文/证据字符合计。

工具结果复用既有 `details.memweave_read` 的版本与范围标记，历史查询的 ref 为 F/D，`returned_chars` 同时计正文和证据，offset 为 0；仅可由实际 `state_read` 历史调用及返回项核验授权。完整成功项可使该实际工具结果享有同样的 10 条消息完整回读生命周期；普通 `{task_id}` 查询维持原策略，不新增豁免。缺失、失败或截断不能伪称原件完整。不新增持久化文件、State 事件或 Pi custom 类型。

## 18. Token 管理与提交准入（2026-10-23 确认）

State 规划预算为 floor(C/8)，C=floor(C_model*3/5)。完整 Goal、活动 F/D、ID、证据 ID 和呈现格式一起计数；证据解释只在历史回读时计入 X。按匹配 tokenizer 计数，无法匹配时明确使用保守估算。条数/字符与 token 同时约束；模型收到末尾动态快照，含实际占用、500/100/100/20 有效值及 80% 管理线。

达到条数或 token 管理线任一条件即准备既有 state_remain 批次，格式和提交点不变，候选与保留规则沿用 §15。初始化、追加、Goal 更新、modify_fact 在 Task 锁内重放拟提交结果，超 State 准入预算的增长整体拒绝，未提交不写入；先识别幂等重试。已有超额 State 的非增长修正及 state_remain 允许，不能先写入增长再等下一请求报错。提醒期间仍允许在 token 预算内超条数追加。

旧 State 切换小模型可挤占普通 Window 以便整理；完整 State 与必要成本放不下时取消请求并提示较大模型整理，不裁剪 State 或自动选认知。同 Task 所有会话共享整理结果。原始日志、State 事件类型、窗口批次持久化格式均不变。

## 20. 回读 token 分池（2026-10-25 用户确认）
