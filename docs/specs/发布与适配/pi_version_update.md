# Pi 新版本适配原则

## 1. 目标与授权范围

当用户主动要求“适配当前最新版本的 Pi”或明确指定某个 Pi 版本时，Agent 应主动完成版本核实、接口审查、必要实现、验证和文档同步，不能只停留在解释、评估或提出计划。

**在不改变当前核心设计规范、功能和原则，且不增加运行时副作用的前提下，Agent 可以自行完成适配，无须为常规接口调整反复请求确认。** 此授权适用于实现层的等价调整，不授权重新设计记忆系统、削减功能或扩大数据与配置的写入范围。

本规范是后续适配任务的执行原则，不表示当前已支持新 Pi，也不因编写本规范而立即启动适配。适配授权不等于 npm 发布授权；发布仍须遵循同目录的 [npm 发布规范](npm.md)。

## 2. 确定目标版本

1. 收到“适配最新版”的要求后，主动从 Pi 官方发布记录、npm 元数据及对应版本源码核实当时的最新正式版本，记录查询日期和精确版本号。用户明确要求预发布版或其他版本时，以该要求为准。
2. 不把 Git `main`、记忆中的版本号或无版本文档当作已发布最新版。官方来源信息不一致时，先核实；无法确定目标时，说明冲突并询问用户。
3. 核实后固定本次适配目标，阅读该版本实际类型定义、源码、发布说明及相关变更；开发与测试依赖精确对应目标版本，不直接用浮动依赖代替验收。
4. 在临时或隔离的测试环境核验新宿主。适配工作本身不要求擅自升级用户正在使用的全局 Pi、改换用户配置目录或改写真实运行数据。

## 3. 可以自行完成的适配

在已确认授权范围内，Agent 可直接完成以下工作：

- 调整公开接口的导入、类型、参数映射、返回值转换，以及保持原有契约的等价接口替换。
- 将必要版本差异收敛到 `src/pi/` 薄适配层及 Package 元数据、构建与测试配置，不为每个宿主版本复制业务实现。
- 根据验证结果调整版本检查、能力诊断、精确开发依赖和兼容矩阵；只开放实际验证通过的范围，不能只放宽版本判断就宣称适配完成。
- 补齐有意义的回归测试、安装与恢复验证，更新直接相关的技术说明和用户说明，并按项目 Git 检查点要求提交适配结果。

接口名称或类型变化本身不是必须停止的理由。只要能通过 Pi 公开机制保持原有核心行为、功能与副作用范围，就继续完成适配，并在交付时说明差异。

### 核心边界

适配须保留现行五份运行时规范、[架构](../../ARCHITECTURE.md)和 [Package 设计](../../PACKAGING.md)规定的契约，尤其包括：

- 继续作为原生 Pi 扩展运行，复用 Agent Loop、Session、模型、工具、界面、信任和 Package 机制；不 fork、patch 或复制 Pi 核心，不另建应用宿主或全量聊天副本。
- Task、State、Recent Window、Rule 的功能、工具语义、预算、原文引用、计数、提交、持久化与恢复语义保持一致，不用摘要、丢弃字段或关闭功能掩盖不兼容。
- 保留既定请求顺序、同一请求快照、错误主动取消、原生消息与工具配对、多模态和供应商必需字段；不擅自改变统一上下文组装的职责或时序。
- 保留现有文件、配置、初始化、Rule 升级覆盖与压缩设置的作用范围。不得新增未经确认的文件覆盖、配置修改、权限要求、运行时网络或模型调用，也不得删除原生 Session 记录或用户数据。

“无额外副作用”以现有已确认行为为基线，须检查新宿主实际执行的效果，而不只检查 MemWeave 自身新增了哪些写入。Pi 自身机制变化若导致新的配置或会话影响，也须纳入评估。

## 4. 旧 Pi 版本兼容

尽量继续兼容已经支持的旧 Pi 版本；能够通过简单、明确的薄适配保留兼容时，应优先保留。

**旧宿主兼容不是完成新版本适配的硬性条件。** 若保留旧版会引入额外复杂性，或新旧公开机制无法合理共存，可以停止支持相关旧 Pi 版本，无须仅为此再次请求确认。须明确说明不再支持的版本、原因及已验证支持范围，并提供清晰的版本或能力诊断，不静默降级核心功能。

停止支持旧 Pi 版本，不等于允许破坏旧 Session、Task、State 等既有数据的读取与恢复契约。若涉及数据格式迁移、恢复语义变化或新增副作用，仍按下一节先与用户讨论。

## 5. 需要讨论的情况

发现下列情况时，暂停受影响部分，向用户说明后再决定；能够独立推进且不依赖该决定的核查与测试可继续：

1. 新宿主公开 API 无法等价满足核心功能，或必须改变现行核心设计、工具语义、请求时序、数据格式、恢复或提交语义。
2. 保持可用需要削减现有功能、放宽预算或来源核验、改变信任或权限边界，或引入额外配置、文件、会话、网络、模型调用等副作用。
3. 只能通过修改 Pi 核心、patch 安装目录、增加另一套宿主或超出现有模块边界的方案实现。
4. 关键行为无法验证、规范存在冲突，或无法确定适配是否仍处于已授权范围。

讨论先用易读语言说明目的、收益、改动范围和副作用，再给出具体接口差异、冲突文档位置、可选方案及推荐理由。用户确认设计变化后，先更新直接相关规范，再实现；不得先改变行为，再补写成已确认设计。

## 6. 主动提出新机制与优化建议

适配中应留意新 Pi 提供的公开机制，主动识别能简化实现、改善性能、降低维护成本或提升可靠性的机会，并向用户提出有依据的建议。

- 属于保持核心契约且无额外副作用的局部等价优化，可以在适配范围内自行完成并说明验证结果。
- 影响核心方案、功能、依赖边界或副作用的优化，只提出建议，说明收益、代价、旧版本影响和验证办法，经用户确认后再实施。
- 可选优化不得阻塞原本能够独立完成的必要适配，也不得因为新机制存在就扩大改动范围或声称其必然更好。

## 7. 验收与交付

按实际改动运行类型检查、相关单元测试、目标 Pi 集成测试及必要分发检查。覆盖受影响的上下文组装、主动取消、压缩控制、Session 原文、工具与多模态结构、Task/State/Window 恢复和初始化等行为；继续宣称支持的旧版本也须有对应验证证据。

Mock、本机 HTTP、实际 Pi 和真实模型 API 的验证结果须分开记录；仅当测试需要真实模型时，按项目既有私有配置和密钥规则执行。编译通过或 Mock 通过不能代替实际宿主验收。

交付说明应列出目标 Pi 精确版本及核实依据、适配文件与接口差异、实际测试结果、保留或停止支持的旧版本、未验证范围和发现的优化建议。未完成验证的组合不得标为支持；适配完成不自动发布 npm 新版。
