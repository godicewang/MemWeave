# MemWeave npm 发布规范

## 1. 适用范围与发布授权

本规范根据用户明确要求制定，约束 MemWeave 的 npm 包名、版本编号、发布时机和渠道选择。Package 内容、宿主兼容与运行时边界仍遵循 [Pi Package 发布层设计](../PACKAGING.md)。

- npm 包名为 `memweave`，首次发布版本为 `0.1.0`。
- **只有用户主动、明确要求发布时，才执行 npm 发布。** 完成开发、修复、测试、构建、Git commit 或 push，均不构成发布授权。
- 要求编写或修改发布规范、准备发布、检查发布条件，也不等于要求实际发布。
- 一次发布指令只执行该指令要求的发布，不自动形成后续持续发布或定时发布。
- 本规范本身不触发发布，不立即修改当前开发快照的版本或解除 `private` 限制。首次实际发布时，再按授权准备对应元数据。
- 发布前核验账号对 `memweave` 的发布权限；包名不可用或无权发布时，报告阻碍，不擅自改用其他包名。

## 2. 版本编号

默认从以下序列连续发布：

```text
memweave@0.1.0 → memweave@0.1.1 → memweave@0.1.2 → …
```

1. 没有已发布版本时，首次使用 `0.1.0`。
2. 用户未指定其他版本时，以所有渠道中已发布的最高版本为基准，只将补丁号加 `1`。`latest` 和 `next` 共用同一条编号序列，不分别计数。
3. 用户未主动说明时，不跳号，不自行提升次版本号或主版本号，也不另加 `-next.1`、`-beta.1` 等预发布后缀。测试渠道通过 dist-tag 区分。
4. 用户明确指定版本或要求跳号时，按该要求处理；仍须核验目标版本有效且未被占用。版本变化不自动授权修改核心设计或数据协议。
5. 已发布的同名同版本不能覆盖或重新使用。发布失败或结果不明时，先核验 registry 中的实际结果；未发布成功不占用下一个编号，不因重试自动跳号。
6. 确定版本时不能只读取 `latest`、`next` 或本地开发版本，须核对 registry 已发布版本和对应发布记录；无法核验时不猜测编号。

## 3. 稳定版与测试版

| 用户要求 | 发布渠道 | 默认行为 |
|---|---|---|
| 明确要求发布稳定版，或明确指定 `latest` | `latest` | 将本次新版本发布到稳定渠道 |
| 要求发布测试版，或明确指定 `next` | `next` | 将本次新版本发布到测试渠道 |
| 只说“发布”“发布新版”等，没有明确说明稳定版 | `next` | 一律按测试版发布，不必为默认渠道再次追问 |
| 没有主动要求发布 | 无 | 不执行 npm 发布，也不变更远端 dist-tag |

`latest` 只指向用户明确要求发布的稳定版本；`next` 用于高频测试版本。测试版即使版本号更大，也不能因此自动移动 `latest`。首次稳定版发布前，不将测试版当作 `latest` 提供给用户。

执行发布时必须显式传入渠道，避免裸 `npm publish` 默认使用 `latest`：

```sh
# 默认：用户要求发布，但没有明确要求稳定版
npm publish --access public --tag next

# 仅在用户明确要求稳定版时使用
npm publish --access public --tag latest
```

以上命令是操作示例，不是执行授权。不得为凑齐两个渠道，将一次发布指令扩展成两次发布或额外修改其他标签。若用户明确要求将一个已发布版本转为稳定版，只调整其 `latest` 标签，不重新上传该版本，也不将标签调整计作一个新版本。

## 4. 编号与渠道示例

下表为连续操作示例，不表示这些版本已经发布：

| 操作前状态 | 用户指令 | 结果 |
|---|---|---|
| 尚未发布 | “发布一下” | 发布 `0.1.0` 到 `next` |
| 已发布最高版本为 `0.1.0` | “再发布一版测试” | 发布 `0.1.1` 到 `next` |
| 已发布最高版本为 `0.1.1` | “发布稳定版” | 发布 `0.1.2` 到 `latest` |
| 已发布最高版本为 `0.1.2` | 完成一轮修复和测试，未要求发布 | 不发布，两个渠道的标签均不变 |
| 已发布最高版本为 `0.1.2` | “发布新版” | 发布 `0.1.3` 到 `next`，`latest` 仍指向 `0.1.2` |

## 5. 执行与结果核验

1. 根据用户指令确定是否发布、是否明确要求稳定版、是否明确指定版本；未指定时直接采用本规范默认值。
2. 核验包名权限、已发布版本与当前标签，确定本次版本。按现有工程流程完成元数据、许可、相关测试、构建与归档内容检查；不扩大宿主兼容承诺。
3. 只发布经检查的本次版本，显式使用 `--tag next` 或 `--tag latest`。账号、认证、网络或检查失败时报告，不将准备完成表述为发布成功。
4. 发布后核验目标版本实际存在、所选标签指向正确，并确认未意外移动另一个渠道的标签。若结果异常，报告实际状态，不自动增加版本重发或擅自调整其他标签。
5. 交付说明写清实际包名、版本、渠道及对应安装命令。稳定渠道使用 `pi install npm:memweave@latest`，测试渠道使用 `pi install npm:memweave@next`；需要固定版本时使用如 `pi install npm:memweave@0.1.2`。

发布新包版本仍遵循现有 Rule 升级行为：用户加载不同 `package.json.version` 的包时，会自动以该包默认模板覆盖运行时 Rule；本规范不修改初始化、记忆数据或压缩设置的既定契约。

## 6. npm 机制依据

- [npm dist-tag 说明](https://docs.npmjs.com/adding-dist-tags-to-packages/)：标签用于区分发布渠道；裸 `npm publish` 默认使用 `latest`，可用 `--tag` 指定其他渠道。
- [npm publish 说明](https://docs.npmjs.com/cli/v11/commands/npm-publish/)：同名同版本一经发布不能重新使用，撤回该版本也不能复用编号。
