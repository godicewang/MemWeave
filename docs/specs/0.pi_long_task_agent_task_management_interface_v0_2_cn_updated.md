# Pi Long Task Agent - Task Management Interface v0.2

## 1. 核心定义

Task 是长期任务的认知单位。

Session 是 Pi 的一次具体交互容器，负责保存：

-   user 消息
-   assistant 输出
-   tool 调用与结果
-   branch 信息

二者关系：

    Session S1:
        Task A
        Task B

    Session S2:
        继续 Task A

因此：

-   Task 不属于单一 Session
-   Session 可以切换多个 Task
-   一个 Task 可以跨多个 Session 延续

------------------------------------------------------------------------

# 2. Task 与 Agent Run 的关系

Task 表示：

> 一个长期目标的认知状态。

Agent Run 表示：

> 一次具体执行过程。

二者必须解耦。

例如：

    Task:
    优化支付系统

    Agent Run:
    本次执行代码分析

未来支持多 Agent 时：

多个 Agent Run 可以服务同一个 Task。

------------------------------------------------------------------------

# 3. Task 不负责方案分支

普通方向变化不创建新 Task。

例如：

    方案 A 失败
        ↓
    尝试方案 B

仍属于同一个 Task。

通过 Symbolic State 管理：

-   Goal
-   Fact
-   Decision

记录任务目标、已确认的重要事实、关键决定，以及任务主要演化路径中的重要转折和结果。

未来如果需要并行探索：

引入：

-   experiment branch
-   run branch

而不是 task_fork。

------------------------------------------------------------------------

# 4. Task 数据实体

每个任务拥有唯一：

    task_id

示例：

``` json
{
  "task_id": "task_xxx",

  "title": "Pi 长程 Agent 设计",

  "summary":
  "设计基于 Pi 的长期记忆 Runtime",

  "keywords":
  [
    "Pi",
    "Agent",
    "Memory"
  ],

  "workspace":
  "cwd_key",

  "state_version":
  12,

  "status":
  "active"
}
```

# 5. Task 工具设计

## 5.1 task_create

### 作用

创建新的长期任务。

### 输入

``` json
{
  "title": "任务名称",
  "goal": "任务目标",
  "project_name": "项目名称",
  "summary": "便于后续发现与恢复的任务摘要",
  "context": "创建原因",
  "keywords": ["keyword"]
}
```

### 由 Agent 与程序共同完成

Agent 在任务开始时生成并提供任务标题、目标、项目名、摘要和关键词；程序生成以下信息：

-   task_id
-   workspace
-   state 路径

创建前由程序校验必需字段，确保任务可被后续发现和恢复。若后续通过 `update_goal` 改变目标，Agent 还应同步更新任务索引中的摘要与关键词；项目名仅在项目归属确实改变时更新。摘要与关键词用于任务发现，不替代 Symbolic State。

### 执行流程

    task_create

    ↓

    生成 task_id

    ↓

    创建任务 State

    ↓

    更新任务索引

    ↓

    绑定当前 Session

------------------------------------------------------------------------

# 5.2 task_find

## 作用

根据自然语言描述寻找历史任务。

模型通常不知道 task_id。

因此提供：

    自然语言描述
            ↓
    程序检索
            ↓
    候选任务

### 输入

``` json
{
  "query":
  "之前设计 Pi memory 的任务",

  "keywords":
  [
    "Pi",
    "memory"
  ],

  "limit":
  5
}
```

### 返回

``` json
[
 {
  "task_id":
  "task_001",

  "title":
  "Pi Memory Agent",

  "summary":
  "设计长期记忆 Runtime",

  "keywords":
  [
   "Pi",
   "Agent"
  ]
 }
]
```

task_find：

只负责发现。

不负责恢复。

跨 Task 原文引用由统一的 `memory_read` 机制提供当前 Task 可使用的 R 引用，并按已知引用读取原文；该工具支持多引用、字符偏移和返回长度限制，具体参数与返回协议见 Symbolic State 文档。R 只是定位别名，不改变来源 Task 原有的 U/A/T/F/D 编号，也不自动恢复来源 Task。`state_read` 只读取历史 Task 的 State，不切换当前任务；`task_resume` 才切换当前任务。

------------------------------------------------------------------------

# 5.3 task_resume

## 作用

恢复已有任务工作现场。

task_resume 不是简单查询，而是一次状态切换。

支持两种模式。

------------------------------------------------------------------------

## 模式一：明确 task_id

输入：

``` json
{
 "task_id":
 "task_xxx"
}
```

------------------------------------------------------------------------

## 模式二：恢复当前工作区最新暂停任务

输入：

``` json
{
 "mode":
 "latest_paused"
}
```

程序根据：

-   当前 cwd/workspace
-   Task 状态
-   更新时间

寻找最近暂停任务。

------------------------------------------------------------------------

## 不支持模糊恢复

不支持：

    resume("之前那个memory任务")

正确流程：

    task_find

    ↓

    模型选择任务

    ↓

    task_resume

------------------------------------------------------------------------

## task_resume 执行流程

    task_resume

    ↓

    定位 Task

    ↓

    加载 Symbolic State

    ↓

    替换当前 Agent 状态

    ↓

    绑定当前 Session

    ↓

    返回恢复信息

------------------------------------------------------------------------

## 返回内容

tool result 进入 Recent Window：

``` json
{
 "task_id":
 "task_xxx",

 "title":
 "...",

 "summary":
 "...",

 "goal":
 "...",

 "state_version":
 12,

 "restored":
 true
}
```

------------------------------------------------------------------------

恢复后：

模型可以感知：

-   当前任务已恢复
-   当前状态是什么
-   下一步是什么

如果用户随后：

    你恢复错了

由于 Recent Window 保留恢复过程，Agent 可以处理。

------------------------------------------------------------------------

用于：

-   调试

输入：

``` json

 "task_id":
 "task_xxx"
}
```

返回：

``` json
{
 "task_id":
 "task_xxx",

 "status":
 "active",

 "state_version":

```

# 6. 明确不实现

## task_fork

暂不实现。

原因：

任务方向变化不等于新任务。

例如：

    方案 A
    失败

    ↓

    方案 B

仍然属于同一 Task。

------------------------------------------------------------------------

## 子 Agent

暂不实现。

后续单独设计：

-   child run
-   execution lifecycle
-   result return

避免：

Task 管理

与

Agent 调度

耦合。

# 7. 第一阶段 Task Tool 总结

最终接口：

    task_create

    task_find

    task_resume

    task_status

职责：

负责：

-   创建任务
-   发现任务
-   恢复任务
-   查询任务

不负责：

-   State 修改
-   方案管理
-   子 Agent 调度

------------------------------------------------------------------------

# 设计原则总结

1.  Task 是认知单位，不是会话单位。

2.  Session 是交互容器，不承担长期任务身份。

3.  Agent Run 与 Task 解耦，为未来多 Agent 扩展保留空间。

4.  模糊寻找与明确恢复分离：

    task_find
        ↓
    task_resume

5.  普通方案变化通过 State 管理，不创建大量 Task。

6.  保持简单，不提前引入 workflow engine、任务状态机和复杂调度系统。


# 8. 阶段 2 持久化与恢复约定（2026-10-21 用户确认）

`index.json` 为 Task 对象数组，包含 `task_id`、`title`、`project_name`、`summary`、`keywords`、`workspace`、`state_version`、`status`，另登记 `updated_at` 与 `sessions: [{session_id, file}]`。workspace/目录键沿用 Pi 的 cwd identity；索引不保存消息正文或逐消息映射。

U/A/T 定位保存在 Pi `custom` 条目 `memweave.references.v1`：data 为 `{task_id, source_session_id, bindings:[{ref, entry_id, tool_call_id?}]}`。仅 T 包含原生 `tool_call_id`，且必须已有真实工具结果。分配编号前持 Task 写锁，核验该 Task 登记的 Session；按原来源去重 fork 复制的记录，继续独立 U/A/T 序列。正常请求缓存并增量核验来源，不每轮重建全历史；缺失/损坏来源明确失败，不清零编号。完整原文仅保存在 Pi Session。

当前分支绑定/配置存于 `memweave.scope.v1` custom 条目，data 为 `{task_id: string|null, overrides: {...}}`，overrides 仅含既有六个配置字段。读取当前祖先链最后一条记录；新普通 Session 无绑定，fork 继承分叉点，tree 回退恢复目标绑定并追加自有 scope 锚定重启叶子。Task 级 State 在分支间共享，不随聊天回退撤销。

切换前消息维持原 Task 归属；后续交互使用新绑定。首次创建只接纳本次未绑定的触发用户消息和创建轮 assistant/工具，不接纳全部历史。resume 保留当前恢复过程，不载入旧聊天、不改变 cwd。创建/恢复将目标置 active；切换/关闭/回退不自动暂停其他 Task。running 仅指当前 Pi 实例正在执行该 Task。latest_paused 可读取既有 paused 记录，本阶段不增加暂停/完成入口。

输入边界：task_create 的 title/goal/project_name/summary/keywords 必填且非空，context 可选；task_find 的 query 必填，keywords 默认 []，limit 默认 5 且为正整数；task_status 的 task_id 必填；task_resume 的 task_id 与 mode=latest_paused 两种输入互斥。同一 assistant 轮多个切换或切换混合 State 写入必须拒绝冲突调用。

跨文件操作的认知提交点为 state.json；索引、state.md 或绑定失败时报告 Task ID、已提交部分和失败阶段，不假报完整成功。Pi 追加失败可能已修改内存，必须停止相关流程，不以内存条目证明落盘。

# 9. 阶段 4 原文来源约定（2026-10-21 用户确认）

原文回读不切换 Task。memory_read.items 增加可选 task_id：省略时读取当前 Task 的 U/A/T 或 R；指定其他 Task 时只接受该来源 Task 已存在的 U/A/T，成功定位后分配并返回当前 Task 可复用的 R。没有当前 Task 时拒绝调用。同一 assistant 轮混合 Task 切换与 memory_read 时拒绝冲突。state_read 仍只返回 State，不承担别名分配。

新增 Pi custom 类型 memweave.aliases.v1：{task_id, bindings:[{ref, source_task_id, source_ref, part_index?}]}。ref 为 Task 作用域 R，source_ref 为最终来源的 U/A/T；part_index 仅定位原 Session 内容数组附件，不形成 R 链。持 Task 写锁按全部已登记 Session 分配编号、按来源去重，fork/重启/重试不重编号。原有 references.v1 格式不变。

新增 memweave.originals.v1：{task_id, bindings:[{ref, source_session_id, entry_id, blob_hash, media_type, byte_length}]}。仅登记需要额外保留的完整原件，首个适配目标为原生 Bash 的完整输出。先将原件可靠写入 blobs/<content_hash>，再追加并核验 custom；不把正文存入元数据。普通小消息和 Session 已有图片不另存副本。失败不能发布不可恢复的别名或伪称完整；崩溃可能留下孤立 blob，本阶段不自动清理。用户数据在禁用/卸载后保留。

R 只提供定位，作为 evidence 时需校验其最终 U/A/T 或附件存在；不得把别名登记本身作为证据。其他 Task 的来源缺失应逐项报告，不能掩盖同批其他成功读取。具体正文/图片协议见 State §16。

2026-10-23 用户确认：历史 F/D 通过 `state_read({task_id,event_ids,max_total_chars?})` 受控查询，最多 50 项、默认 8000/最大 50000 字符；不切换 Task、不分配 R、不扩大 memory_read，详见 State §17。
