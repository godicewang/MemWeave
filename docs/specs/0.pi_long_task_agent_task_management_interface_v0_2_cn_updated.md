# MemWeave - Task Management Interface v0.2

> 接入说明（2026-10-20）：本接口由 MemWeave SDK 宿主内的工具实现，通过 `src/pi/` 适配应用锁定的 Pi（当前 v1.3.0）。下文 Session 始终指 Pi 原生 Session，不新增 MemWeave 全量会话库；宿主/发布方式不改变 Task 身份、工具参数、索引或恢复语义。具体 SDK 函数可等价调整，涉及这些业务契约的变化仍须先确认。

## 1. 核心定义

Task 是长期任务的认知单位。

Session 是 Pi 的一次具体交互容器，负责保存：

-   user 消息
-   assistant 输出
-   tool 调用与结果
-   branch 信息

二者关系：

    Session S1:
        Task A
        Task B

    Session S2:
        继续 Task A

因此：

-   Task 不属于单一 Session
-   Session 可以切换多个 Task
-   一个 Task 可以跨多个 Session 延续

------------------------------------------------------------------------

# 2. Task 与 Agent Run 的关系

Task 表示：

> 一个长期目标的认知状态。

Agent Run 表示：

> 一次具体执行过程。

二者必须解耦。

例如：

    Task:
    优化支付系统

    Agent Run:
    本次执行代码分析

未来支持多 Agent 时：

多个 Agent Run 可以服务同一个 Task。

------------------------------------------------------------------------

# 3. Task 不负责方案分支

普通方向变化不创建新 Task。

例如：

    方案 A 失败
        ↓
    尝试方案 B

仍属于同一个 Task。

通过 Symbolic State 管理：

-   Goal
-   Fact
-   Decision

记录任务目标、已确认的重要事实、关键决定，以及任务主要演化路径中的重要转折和结果。

未来如果需要并行探索：

引入：

-   experiment branch
-   run branch

而不是 task_fork。

------------------------------------------------------------------------

# 4. Task 数据实体

每个任务拥有唯一：

    task_id

示例：

``` json
{
  "task_id": "task_xxx",

  "title": "Pi 长程 Agent 设计",

  "summary":
  "设计基于 Pi 的长期记忆 Runtime",

  "keywords":
  [
    "Pi",
    "Agent",
    "Memory"
  ],

  "workspace":
  "cwd_key",

  "state_version":
  12,

  "status":
  "active"
}
```

# 5. Task 工具设计

## 5.1 task_create

### 作用

创建新的长期任务。

### 输入

``` json
{
  "title": "任务名称",
  "goal": "任务目标",
  "project_name": "项目名称",
  "summary": "便于后续发现与恢复的任务摘要",
  "context": "创建原因",
  "keywords": ["keyword"]
}
```

### 由 Agent 与程序共同完成

Agent 在任务开始时生成并提供任务标题、目标、项目名、摘要和关键词；程序生成以下信息：

-   task_id
-   workspace
-   state 路径

创建前由程序校验必需字段，确保任务可被后续发现和恢复。若后续通过 `update_goal` 改变目标，Agent 还应同步更新任务索引中的摘要与关键词；项目名仅在项目归属确实改变时更新。摘要与关键词用于任务发现，不替代 Symbolic State。

### 执行流程

    task_create

    ↓

    生成 task_id

    ↓

    创建任务 State

    ↓

    更新任务索引

    ↓

    绑定当前 Session

------------------------------------------------------------------------

# 5.2 task_find

## 作用

根据自然语言描述寻找历史任务。

模型通常不知道 task_id。

因此提供：

    自然语言描述
            ↓
    程序检索
            ↓
    候选任务

### 输入

``` json
{
  "query":
  "之前设计 Pi memory 的任务",

  "keywords":
  [
    "Pi",
    "memory"
  ],

  "limit":
  5
}
```

### 返回

``` json
[
 {
  "task_id":
  "task_001",

  "title":
  "Pi Memory Agent",

  "summary":
  "设计长期记忆 Runtime",

  "keywords":
  [
   "Pi",
   "Agent"
  ]
 }
]
```

task_find：

只负责发现。

不负责恢复。

跨 Task 原文引用由统一的 `memory_read` 机制提供当前 Task 可使用的 R 引用，并按已知引用读取原文；该工具支持多引用、字符偏移和返回长度限制，具体参数与返回协议见 Symbolic State 文档。R 只是定位别名，不改变来源 Task 原有的 U/A/T/F/D 编号，也不自动恢复来源 Task。`state_read` 只读取历史 Task 的 State，不切换当前任务；`task_resume` 才切换当前任务。

------------------------------------------------------------------------

# 5.3 task_resume

## 作用

恢复已有任务工作现场。

task_resume 不是简单查询，而是一次状态切换。

支持两种模式。

------------------------------------------------------------------------

## 模式一：明确 task_id

输入：

``` json
{
 "task_id":
 "task_xxx"
}
```

------------------------------------------------------------------------

## 模式二：恢复当前工作区最新暂停任务

输入：

``` json
{
 "mode":
 "latest_paused"
}
```

程序根据：

-   当前 cwd/workspace
-   Task 状态
-   更新时间

寻找最近暂停任务。

------------------------------------------------------------------------

## 不支持模糊恢复

不支持：

    resume("之前那个memory任务")

正确流程：

    task_find

    ↓

    模型选择任务

    ↓

    task_resume

------------------------------------------------------------------------

## task_resume 执行流程

    task_resume

    ↓

    定位 Task

    ↓

    加载 Symbolic State

    ↓

    替换当前 Agent 状态

    ↓

    绑定当前 Session

    ↓

    返回恢复信息

------------------------------------------------------------------------

## 返回内容

tool result 进入 Recent Window：

``` json
{
 "task_id":
 "task_xxx",

 "title":
 "...",

 "summary":
 "...",

 "goal":
 "...",

 "state_version":
 12,

 "restored":
 true
}
```

------------------------------------------------------------------------

恢复后：

模型可以感知：

-   当前任务已恢复
-   当前状态是什么
-   下一步是什么

如果用户随后：

    你恢复错了

由于 Recent Window 保留恢复过程，Agent 可以处理。

------------------------------------------------------------------------

# 5.4 task_status

## 作用

查询任务状态。

用于：

-   当前任务检查
-   后续 Agent Run 扩展
-   调试

输入：

``` json
{
 "task_id":
 "task_xxx"
}
```

返回：

``` json
{
 "task_id":
 "task_xxx",

 "status":
 "active",

 "state_version":
 12,

 "running":
 false
}
```

未来扩展：

``` json
{
 "active_runs":
 [
  {
   "run_id":
   "run_xxx",

   "status":
   "running"
  }
 ]
}
```

# 6. 明确不实现

## task_fork

暂不实现。

原因：

任务方向变化不等于新任务。

例如：

    方案 A
    失败

    ↓

    方案 B

仍然属于同一 Task。

------------------------------------------------------------------------

## 子 Agent

暂不实现。

后续单独设计：

-   child run
-   execution lifecycle
-   result return

避免：

Task 管理

与

Agent 调度

耦合。

------------------------------------------------------------------------

# 7. 第一阶段 Task Tool 总结

最终接口：

    task_create

    task_find

    task_resume

    task_status

职责：

负责：

-   创建任务
-   发现任务
-   恢复任务
-   查询任务

不负责：

-   State 修改
-   方案管理
-   子 Agent 调度

------------------------------------------------------------------------

# 设计原则总结

1.  Task 是认知单位，不是会话单位。

2.  Session 是交互容器，不承担长期任务身份。

3.  Agent Run 与 Task 解耦，为未来多 Agent 扩展保留空间。

4.  模糊寻找与明确恢复分离：

```{=html}
<!-- -->
```
    task_find
        ↓
    task_resume

5.  普通方案变化通过 State 管理，不创建大量 Task。

6.  保持简单，不提前引入 workflow engine、任务状态机和复杂调度系统。
