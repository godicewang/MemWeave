# State 长历史性能修复与工具约束澄清

## 第一部分：目的、范围和取舍

2026-10-25 用户授权修复长期使用的 State 读写瓶颈及工具约束提示；暂不修改积压 Window 的处理方式和恢复后指令优先级。

原实现每次修改都会解析、校验和重放全部 State 历史，再次读取旧文件并重放拟提交结果。活动认知只有约 500 条时，旧日志仍可能已有 5 万条；重复工作延长 Task 写锁占用，并发请求会超时。

复用已经校验的进程内状态，每次仍读取并比较实际文件。旧内容完全一致时复用；只有新记录时校验并重放新增部分；历史替换、修改或截断时完整重建。修改只影响本机准备时间，不改变认知选择、模型上下文、持久化格式、锁超时或提交语义。

代价是有界内存占用：每个 StateStore 最多缓存 4 个 Task，按估算总量最多 128 MiB；不新增磁盘缓存。超限时淘汰或不缓存，仍可完整读取。该数值是缓存记账上限，不是整个 Pi 进程 RSS 的保证；读取、复制和原子替换仍随日志长度增长，冷启动及超大日志仍有完整重放成本。

工具方面只澄清既有约束：state_append 每项必须显式提供 type；Goal、Fact、Decision 的正文均按配置的 Unicode 码点上限验证。提供最小示例，超长错误报告字段、实际长度和上限；不自动补参数、不截断、不放宽非法输入。

## 第二部分：实现和验收边界

- state.json 仍是唯一认知提交源，完整 JSONL 原前缀及原子替换、Task 锁、op_id 和批次规则保持不变，不新增快照文件或恢复协议。
- 缓存保存已校验文件文本、State 和操作/批次定位索引。总量记账保守计入文本、事件与条目开销，LRU 淘汰；不跨 StateStore 实例共享。
- 每次读操作都严格解码实际文件，不能只信 mtime、文件大小或 inode。相同文本才能复用；完整前缀后新增合法 JSONL 才能增量重放。尾部空行等宽容读取情形不走增量捷径，继续按原完整解析规则处理。
- reducer 增量应用时隔离容器，对修改的旧条目使用副本；失败不污染已校验状态。外部返回和提交 guard 获得独立可修改副本，调用参数也不能成为内部共享可变数据。
- 实际提交成功后才发布新缓存；读取或提交失败清除对应缓存，下次以实际文件为准。持久性不确定仍使用既有错误与同 op_id 重试。
- 约束说明落在工具描述、参数 schema、固定 Rule；Rule 两份规范和资源同步。已有同版本自定义运行时 Rule 不额外覆盖，工具描述在重新加载源码后生效。
- 验收覆盖增量/完整重放等价性、失败隔离、外部替换与损坏、幂等/并发、缓存上限、动态字符限额及真实 DeepSeek 调用。性能对比使用同一临时脚本和相同数据，不将 mock 结果当作真实 API 结果。

12 个 Task、每个 2001 条操作，连续 20 轮读取并触发淘汰：缓存最多 4 个 Task、最高估算 18163952 bytes，GC 后 heapUsed 约 21.48–21.55 MiB。计账上限及超大条目不缓存另由正式单测覆盖。该有限样本未观察到持续增长，不代表完整 Pi RSS 或数周使用的保证。

### 保持与限制

没有修改积压批次或取消后最新指令优先级，也没有增加恢复命令、记忆自动生成器、通用配置字段、磁盘缓存或模型调用。Window/State/Session 持久化及模型预算、原始 Pi 消息和全局设置保持原边界。固定 Rule 两份规范和打包资源同步；用户已有同版本运行时 Rule 未被本次开发手动覆盖。重新加载本地 Package 后工具描述/诊断生效，npm 公网包未发布。
