# 适配与首发的方法

这些方法来自实际 Pi 1.3.0 → 1.4.0 及 npm/GitHub 首发；用于下一次验证，不把历史成功视为当前候选通过。

## 1. 先看真实宿主，再改适配层

- 对“最新”记录查询时间、官方 release、npm 精确版本及 Node engines；区分正式版、预发布版、Git main 与旧文档。
- 比较 Extension 类型、runner、context_with_system、before_provider_request、SettingsManager、SessionManager、AgentSession、PackageManager、loader 以及相关模型/认证接口。类型未变也要看实现、时序和实际副作用。
- 将差异收敛在 src/pi/ 和包元数据/测试配置；不复制 Pi 核心或业务实现。只有实测通过后才能更新精确支持范围。
- 旧版本测试必须真实加载旧宿主，不能把旧包的版本检查删掉，或在新宿主假报旧版本。此前 1.4.0 回归中旧产物正确拒绝新宿主，修复的是 fixture：让旧产物在真实 1.3.0 上创建，再交给 1.4.0 恢复。
- 冷启动安装宿主的耗时和业务超时分开看。仅在确认时间花在准备依赖而非业务卡死时调整 fixture 超时；保留首轮失败与修正原因。

## 2. 从安装后的代码验证功能

先检查源码，再打包；用真正解包/安装的扩展入口执行功能。不要只加载开发仓库后就宣称发布包可用。

固定候选 commit 和实际归档 integrity，确认 Rule/tokenizer/默认配置/许可完整。安装包目录、业务 cwd、Pi profile、memory、Session 和 npm cache 分开，测试资料放在临时目录；复用宿主 peer，不顺手安装第二套 Pi。检测 npm 白名单，也检测 Git 包内 AGENTS/开发资料没有进入业务上下文。

恢复要跨独立进程：先创建 Task 与 State、保存 Session，退出后再次打开，读 U1 原文、提交 State 并调整窗口。比较旧 State 前缀与原始消息条目；仅检查文件存在或工具返回 success 不足以证明恢复。

## 3. 分清测试替身、实际 Pi 和真实模型

- 单元测试：算法、schema、reducer、模板等边界。
- 实际 Pi + 本机 HTTP：真实 Agent Loop、hook、工具、Session、请求取消与恢复；模型回复受控，不产生真实推理。
- 真实 DeepSeek：验证实际认证、容量、供应商请求、工具调用与续跑；复用仓库外私有配置，记录实际次数并确认 auth 不变。
- 真实 CLI/PTY：验证界面回车确认、取消、reload、退出、独立重启。SDK 中模拟 UI 的测试不能替代终端证据。

等待异步生命周期时，使用实际 Promise 完成或可验证的完成事件，不以“已进入 reload”、某个设置刚更新或固定 sleep 判定就绪。本次建立发布入口时，常规回归捕获 stale-context 错误；检查发现旧初始化 fixture 以“reload 已进入 + 20ms”判定就绪，不能保证它已完成；已改为等待真实 session.reload 完成计数，并在升级用例中加入 75ms 的启动延迟。保留首轮失败，不改运行代码、不忽略 stale-context 异常来让测试变绿。

不要为基础检查自动读取或输出密钥；真实请求与输出不直接粘进报告。图片测试保留误识别记录，单次复测成功不能证明 OCR 永远正确。

## 4. 用隔离环境保留兼容与恢复证据

每个拟支持的 Pi 使用独立临时 checkout/profile，安装该精确版本的 pi-ai 与 coding-agent，再运行基础发布入口；保持业务源码相同。不要修改真实全局 Pi、私有 auth 或用户 memory 来切版本。

跨版本应分别记录“扩展旧/新版本”和“Pi 旧/新宿主”。固定 npm 版本在 Pi update 中可能被跳过，需实际调用 install 新版本并查看安装目录；Git 要记录完整 commit，不能把旧 origin/main 或一次未经固定 ref 的成功当作新候选验证。

## 5. 检查副作用和失败路径

首次确认替换 Rule、全局关闭压缩，是已经确认的作用范围；应核验项目显式开启仍会阻断、其他配置不被覆盖、同版本不重复覆盖、升级后覆盖且标记最后提交。卸载保留数据及压缩配置不是清理失败。

区分本扩展不改原始消息与 Pi 原生 context_edit 恢复记录；取消摘要不等于有效会话视图从未变更。测坏配置/模板/预算时，观察实际 HTTP 计数为 0，不只断言抛出了异常。

## 6. 发布结果以 registry 和下载为准

同名同版本不可覆盖；命令成功后可能先出现 404，先等待传播并核验，不重复上传、不跳号。记录 next/latest 前后指向；异常先报告，不擅自改标签或发布占位版本。身份验证交给用户完成，不打印令牌。

npm scope 与 GitHub scope 可能不同。改包名先确认；GitHub 镜像从已发布 npm 原件生成，只允许约定元数据差异，并逐字节比较其余文件。GitHub 页面标记 Latest 不等于用户授权稳定版；是否公开要看实际页面/权限，下载仍可能要求 GitHub 认证。

SSH 成功不代表 HTTPS 成功；网络失败应区分协议和目的站点，不能借机改全局代理或 Git 配置。首发工作流成功、registry 下载和独立安装/恢复是不同层证据，各自记录。
